# 自建 Graph Agent:需求分析与可行性分析

> 日期:2026-09-05  
> 结论:**需求真实存在、方向与业界已验证的生产范式一致、MVP 切割合理,可行;真正的风险不在"做不出来",而在范围蔓延与差异化定位。**

---

## 0. 结论先行

1. **你的想法不是空中楼阁。** "Graph + 状态机 + 主 Agent 协调 + 节点级 subAgent" 这一组合,正是 LangGraph(2025-10 发布 1.0,Klarna/Uber/LinkedIn/Replit 生产在用)与 orchestrator-worker 模式的交集。需求已被市场验证。
2. **不会复杂到无法实现。** 把终点形态分解后,每个组件都是已解决的工程问题;单人从 MVP 起步,2~4 周可跑出可用内核。
3. **但"已被验证"是双刃剑。** 这个赛道有成熟开源方案。自研要成立,必须回答一个问题:你的差异化在哪?候选答案有三个(详见 §3.4):**收敛判据作为一等公民、声明式 Graph 配置、节点级模型/工具/MCP 绑定**。这三点恰好是现有框架做得不够痛的地方。
4. **系统论视角是有效的,但需做一次数学修正:** 你要建的不是严格意义的有限状态机(FSM),而是"**带共享状态的有向图执行器**"——控制流走 FSM,数据流走 shared state。两者必须分开建模,否则会在中途撞墙(详见 §2)。

## 1. 需求分析

### 1.1 要解决的核心问题(问题陈述)

| #   | 痛点                    | 根因                   | 你的对策                                                  |
| --- | --------------------- | -------------------- | ----------------------------------------------------- |
| P1  | 长程任务下上下文丢失            | 模型上下文窗口有限,历史被截断后目标漂移 | 状态外置:任务状态存于 Graph 的 shared state / checkpoint,不依赖对话历史 |
| P2  | 模型对 prompt 的遵循能力随轮次衰减 | 长上下文中指令显著性下降         | 用状态机的结构约束替代自然语言约束:下一步去哪由 Graph 边决定,不由模型"自由发挥"         |
| P3  | 输出不可控、格式漂移            | 自由文本生成               | 节点输入/输出 schema 化,主 Agent 校验后传递                        |
| P4  | 单 Agent 上下文爆炸、角色混乱    | 一个 prompt 塞入所有职责     | 主 Agent 只做路由与裁决,节点 subAgent 各自持有小而专的上下文               |


### 1.2 需求分层(P0/P1/P2)

| 层级          | 需求                                                        | 说明                                      | 验收标准                                           |
| ----------- | --------------------------------------------------------- | --------------------------------------- | ---------------------------------------------- |
| **P0(MVP)** | 单模型、单协议(OpenAI 兼容 API)、有限工具集、单 Agent Loop                 | 一个 while 循环:LLM 调用 → 工具执行 → 结果回填 → 终止判断 | 给定一个需要 3~5 步工具调用的任务(如"查文件、读内容、写摘要"),能稳定跑完并输出结果 |
| **P1**      | 声明式 Graph:用配置(YAML/JSON)定义节点与边;节点绑定模型/工具;默认 Agent Loop 兜底 | 通用任务走默认 Loop;特定场景加载对应 Graph             | 不改代码,仅改配置,即可为"代码审查"和"资料调研"两类任务定义不同执行图并跑通       |
| **P1**      | Checkpoint 与恢复                                            | 状态持久化,崩溃/中断后可从最近节点续跑                    | 杀掉进程后重启,任务从断点继续而非重来                            |
| **P1**      | 三类退出条件                                                    | 收敛(达标)、发散(无进展/循环)、挂起(等待外部输入)            | 三类场景各有可复现的测试用例触发对应退出路径                         |
| **P2**      | Multi-agent:主 Agent 为观测者/协调者,节点为 subAgent                 | 主 Agent 不做具体执行,只做路由、传递、裁决               | 一个 3 节点 Graph 中,主 Agent 的 prompt 不含任何节点的业务指令   |
| **P2**      | 节点级 MCP/skill 安装                                          | 每个节点声明自己需要的工具来源                         | 节点配置中声明 MCP server,运行时按需挂载                     |
| **P3**      | 沙箱、多协议、可视化调试                                              | 执行隔离、Anthropic/本地模型协议、trace UI          | 后置,不影响内核成立                                     |

### 1.3 非功能需求

- **可观测性优先**:每一次状态迁移必须可记录、可回放。这不是锦上添花——它是"发散检测"和"调试"的基础设施,从 MVP 起就要留日志钩子。
- **成本可控**:单任务 token 预算上限,超限强制退出(这是兜底退出条件的一部分)。
- **配置即数据**:Graph 定义必须是纯数据文件,可校验(schema validation)、可版本化、可 diff。

## 2. 理论框架的工程映射:系统论 → 可计算机制

你的系统论直觉是对的,但每个概念都必须落到**可计算**的机制上,否则又会退化成"让模型自己判断"——那等于没解决问题。

| 系统论概念             | 数学对应                      | 工程机制                                                              | 现有框架参照                              |
| ----------------- | ------------------------- | ----------------------------------------------------------------- | ----------------------------------- |
| 系统/节点/信息交流        | 有向图 G=(V,E)               | Graph 定义 + 节点间消息传递                                                | LangGraph 节点与边                      |
| 有限状态机             | FSM(控制流)                  | 当前活动节点 + 转移条件                                                     | LangGraph conditional edges         |
| 系统状态              | 全局状态向量 S                  | **shared state + reducer**(数据流,与 FSM 分离)                          | LangGraph TypedDict state + reducer |
| 收敛于稳定态            | Sₜ₊₁ ≈ Sₜ 且目标谓词达成         | **目标校验器**:节点产出通过确定性校验(测试通过/格式合规/校验函数返回 true)即收敛                   | LangGraph 无内置,需自建                   |
| 发散退出              | ‖Sₜ₊₁ − Sₜ‖ 持续不减小,或轨迹进入循环 | **No-progress 检测**:最近 N 步 state diff 无实质变化、相同节点重复访问超阈值、token 预算耗尽 | 各框架均只有 max_iterations 这种粗粒度         |
| 等待外部输入            | 系统开环,需外部激励                | **interrupt + checkpoint**:序列化状态,挂起,外部输入到达后恢复                     | LangGraph interrupt(已验证的模式)         |
| 主 Agent = 观测者/协调者 | 分层控制                      | orchestrator-worker:主 Agent 读 state、选边、校验节点输出,不执行节点任务             | Anthropic orchestrator-worker 模式    |

**关键修正:FSM 不够,你需要的是"FSM(控制流) + shared state(数据流)"双结构。**

原因:严格 FSM 的状态本身不含数据。但你的"系统趋于稳定"判断依赖于数据(节点产出的内容)。LangGraph 的核心设计恰恰是这个分离——这也是它胜过早期 AutoGen 对话式模型的根本原因。你如果在设计初期把数据塞进"状态"里(即把 FSM 的状态当数据载体),节点数会爆炸且无法泛化。

**关于"收敛"必须泼一盆冷水:** 对开放式任务(如"写一份分析报告"),不存在通用的可计算收敛判据。可行路径是把任务分两类:

- **A 类:可验证任务**(代码生成→测试通过;数据转换→schema 校验)——收敛判据可计算,你的状态机价值最大;
- **B 类:不可验证任务**(写作、开放式调研)——收敛判据退化为"主 Agent 裁决 + 迭代次数上限 + 人工确认节点"。对 B 类,Graph 的价值在于流程约束与上下文隔离,而非收敛保证。

## 3. 可行性分析

### 3.1 技术可行性逐项评估

| 组件                       | 难度   | 主要风险                                    | 评估                                          |
| ------------------------ | ---- | --------------------------------------- | ------------------------------------------- |
| Agent Loop(ReAct 式)      | ★    | 无实质风险,模式成熟                              | 数千行内可实现                                     |
| 单协议接入(OpenAI 兼容)         | ★    | 无                                       | 直接覆盖 OpenAI/DeepSeek/本地 vLLM 等一大批模型         |
| 有限工具调用(function calling) | ★★   | 工具结果的 token 膨胀                          | 需设计工具结果截断/摘要策略                              |

| 沙箱                       | ★★★★ | Windows 上隔离方案选择有限                       | **后置合理**,MVP 阶段用"工具白名单 + 人工确认"替代            |

### 3.2 需求真实性:市场验证情况

截至 2026 年的生态事实:

- **LangGraph 1.0**(2025-10 发布)已成为 LangChain 生态默认运行时,核心模型就是"图 + 状态机 + checkpoint + interrupt",生产用户包括 Klarna、Uber、LinkedIn、Replit、Elastic;
- **durable execution**(可持久化执行)已是独立赛道共识——长程 Agent 崩溃续跑、HITL 挂起等待,被认为是生产级刚需而非伪需求;
- CrewAI(角色团队)与 AutoGen(对话流,已进入维护模式,微软转向 MAF)从两侧验证了:没有显式状态机的多 Agent 系统,在复杂任务下调试困难、不可复现、token 成本高。

**结论:需求真实且强烈,但供给端已有强者。** 这直接引出下一节。

### 3.3 "会不会太复杂"——复杂度分解

不会,前提是你接受以下分解原则:

- **内核极小**:Graph 执行器 + state/reducer + checkpoint,约等于一个"带持久化的拓扑排序遍历器"。这是整个系统里最难的部分,但本质上是大二数据结构 + 序列化。
- **智能外包**:推理质量、工具选择、收敛裁决全部委托给模型,内核不做任何"智能"决策。
- **能力渐进**:§1.2 的分层即路线图,每层独立可用、独立可验证。

真正的复杂度风险是**范围蔓延**:可视化编辑器、多租户、权限系统、插件市场——每一个都能单独吃掉几个月。建议把这些明确划入"不做清单"(至少第一年)。

### 3.4 自研 vs 基于 LangGraph 构建

| 维度    | 自研                             | 基于 LangGraph               |
| ----- | ------------------------------ | -------------------------- |
| 时间到可用 | 慢(MVP 2~4 周,完整形态数月)            | 快(天级)                      |
| 学习价值  | 极高——你会真正理解每个机制的为什么             | 中等——学会的是 LangGraph 的 API   |
| 差异化空间 | 收敛判据一等公民、声明式配置、节点级模型混部——可以做进内核 | 受框架抽象限制,收敛检测只能靠外挂          |
| 维护成本  | 全部自担                           | 跟随上游,受其演进节奏约束              |
| 生态    | 从零开始                           | 直接获得 MCP 集成、LangSmith 可观测等 |

**判断:对你的情况(C++ 主力、有系统设计兴趣、目标是构建一套自己的东西而非赶业务上线),自研是合理选择。** 理由有二:第一,这个项目的价值很大程度上在于构建过程本身——它是理解 Agent 系统最有效的方式;第二,你的三个差异化点(收敛判据、声明式 Graph、节点级异构模型绑定)恰好需要掌控内核才能实现。但**协议层不要自研**:MCP 客户端、模型 API 客户端直接用官方/社区 SDK,把精力留给内核。

## 4. 关键设计决策(最容易踩坑的五处)

1. **控制流与数据流分离。** FSM 只管"现在在哪、下一步去哪";任务数据走 shared state,节点通过 reducer 写入。混为一谈会在第二个真实任务上撞墙。
2. **收敛判据必须可计算,且允许"不适用"。** 每个 Graph 配置里显式声明:目标校验器(可选)、最大步数、token 预算、无进展窗口 N。没有声明校验器的任务,诚实退化为"主 Agent 裁决 + 上限兜底",不要假装能收敛。
3. **节点契约 schema 化。** 每个节点声明 input/output JSON Schema,主 Agent 在节点间传递前校验。这是"约束模型输出"最硬的手段,比任何 prompt 工程都可靠。
4. **主 Agent 的 prompt 纪律。** 主 Agent 的系统提示里只允许出现:Graph 结构摘要、当前 state 摘要、可选的下一步。任何业务知识泄漏进主 Agent,都会腐蚀"观测者"的角色纯度。
5. **发散检测用代理指标,不追求完美。** 可计算的启发式:同一节点连续重复 k 次、最近 N 步 state 关键字段 diff 为空、工具返回内容重复率。接受误杀——误杀的代价(重新跑)远小于放任发散的代价(烧穿预算)。

## 5. 分阶段路线图

| 阶段                       | 内容                                                           | 建议周期  | 退出标准                                   |
| ------------------------ | ------------------------------------------------------------ | ----- | -------------------------------------- |
| **Phase 0: MVP**         | 单 Agent Loop + OpenAI 兼容协议 + 3~5 个内置工具(文件读写、shell、搜索)+ 结构化日志 | 2~3 周 | 3 个真实任务稳定跑通;日志可完整回放一轮对话                |
| **Phase 1: Graph 内核**    | Graph DSL(YAML)、执行器、state/reducer、默认 Loop 作为"单节点 Graph"的特例   | 3~4 周 | 用配置定义一个 3 节点任务(如:检索→分析→写报告)并跑通;不改代码可换图 |
| **Phase 2: 持久化与退出条件**    | SQLite checkpoint、interrupt/resume、三类退出条件、token 预算           | 3~4 周 | 三类退出各有自动化测试;杀进程恢复验证通过                  |
| **Phase 3: Multi-agent** | 主 Agent 协调层、节点 subAgent 隔离上下文、节点级模型绑定                        | 4~6 周 | 节点可用不同模型;主 Agent prompt 中无业务指令(代码评审确认) |
| **Phase 4: 生态**          | MCP 集成、节点级工具声明、可视化 trace、(可选)沙箱                              | 持续    | 按需                                     |

注意 Phase 1 的一个设计技巧:**把 MVP 的 Agent Loop 重构为"只有一个节点的 Graph 的特例"**,而不是另起一套。这能迫使你的 Graph 抽象从第一天起就是内核,而不是外挂。

## 8. 技术选型:语言与架构(2026-09-05 补充)


### 8.1 语言选择

**结论:Go。** 综合评分最高,且与你的技术栈偏好一致。

| 语言         | MCP SDK           | Agent 生态                      | 并发模型                | 迭代速度       | 部署形态                | 适配度评估                                                                               |
| ---------- | ----------------- | ----------------------------- | ------------------- | ---------- | ------------------- | ----------------------------------------------------------------------------------- |
| **Go**     | **Tier 1 官方 SDK** | 中(API 调用即 HTTP,无生态短板)         | goroutine,与编排负载天然匹配 | 快          | 单二进制 + 内嵌 SQLite,极简 | **推荐**:你是熟练使用者;编排是 IO 密集型并发,goroutine 是最省心的模型                                       |
| Rust       | Tier 2            | 中                             | tokio,强但复杂          | 慢(类型系统成本高) | 单二进制                | 备选:schema/状态建模的类型安全最好,但 Agent 内核迭代频繁, Rust 的编译期约束会拖慢 Phase 0~2 的探索节奏                |
| TypeScript | Tier 1(参考实现)      | **最强**(LangGraph.js、MCP 生态核心) | 事件循环,够用             | 快          | Node 运行时,部署不如单二进制干净 | 生态优先时的选择;代价是与你既有技术栈偏离                                                               |
| Python     | Tier 1            | 最强(LangGraph 原生)              | asyncio,够用          | 最快         | 打包/依赖管理是长期痛点        | 仅适合快速验证想法,不适合作为长期内核                                                                 |
| C++        | **无官方 SDK**       | 弱                             | 强大但全需自建             | 慢          | 优秀                  | **不推荐**:尽管是你的工作语言——负载是 IO 密集, C++ 的性能优势用不上,而生态缺口(无 MCP SDK、HTTP/JSON 样板繁重)会实打实拖慢每一步 |

**Go 的具体理由(按权重排序):**

1. **工作负载匹配**:Agent 编排 = 大量并发 IO(模型 API、MCP 调用、工具执行)+ 少量状态计算。goroutine + channel 是这个负载下心智成本最低的并发模型。
2. **MCP Tier 1 官方 SDK**(`modelcontextprotocol/go-sdk`):2026-07-28 新规范(无状态协议核心、MRTR、header 路由)已同步支持,不需要自己追协议演进。
3. **部署形态**:单二进制 + 内嵌 SQLite(modernc.org/sqlite,纯 Go 无 cgo),与"个人 Agent"的定位完全吻合;交叉编译覆盖 Windows/Linux/macOS。
4. **你的熟练度**:LaPluma 的维护经验意味着零学习成本,且泛型方法已足以支撑 state/reducer 的类型化建模。
5. **退路存在**:若后期不想自己维护 checkpoint/恢复语义,Temporal 的 Go SDK 是一等公民,可平滑迁移(见 §8.2 方案 C)。

**Go 推荐依赖清单(起步集):** MCP → `modelcontextprotocol/go-sdk`;模型 API → `openai/openai-go`(官方);YAML → `gopkg.in/yaml.v3`;JSON Schema 校验 → `santhosh-tekuri/jsonschema`;SQLite → `modernc.org/sqlite`;CLI → `spf13/cobra`。


### 8.1.1 Rust vs Go 深度对比(用户偏好 Rust 时的完整代价清单)

用户明确表示个人更倾向 Rust 的设计。以下为"编译器约束拖慢迭代"之外的完整缺点清单,按影响程度排序:

| # | 缺点                  | 具体表现                                                                                                                                                                                                                              | 严重程度                    | 缓解方式                                                                                       |
| - | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------ |
| 1 | **MCP SDK 等级差**     | Go SDK 是 Tier 1,Rust 是 Tier 2。2026-07-28 新规范(无状态核心、MRTR、header 路由)Tier 1 同步落地,Tier 2 滞后;Tier 2 意味着维护承诺与功能完整度都弱一档                                                                                                                  | **高**——这是唯一无法靠自身努力消除的差距 | 接受滞后;MCP 客户端仅用到 tools/call 等核心子集时,Tier 2 覆盖已足够;极端情况可直接实现协议子集(新规范无状态化后,客户端复杂度显著下降)          |

**Rust 的真实收益(为完整性列出,避免单边论证):**

- 内核是长生命周期、正确性敏感组件时,Rust 的"重构不翻车"特性在 Phase 2 之后开始净赚——事件溯源、checkpoint 迁移这类手术,编译器会拦住一大类回归;
- serde 生态是全语言最好的序列化方案,checkpoint/事件日志/schema 校验全部受益;
- 无 GC 暂停,长驻进程行为更可预测;
- type-state 模式可以把"Phase 状态机"(如 checkpoint 生命周期)在建模层做死,这是 Rust 独有的表达力。

**修正后的判断:** 原推荐 Go 的前提是"迭代速度优先"。若把个人偏好与长期维护愉悦度纳入权重(单人项目,这两个权重合情地高),**Rust 可行,且缺点 1~5 全部有明确缓解路径**。决策规则建议:如果这个项目对你的意义是"长期陪伴的内核"而非"尽快跑通验证想法",选 Rust 不亏;反之选 Go。两者都不影响 §8.2 的架构结论(方案 A 主线、分层纪律)——那些是语言无关的。

**若选 Rust,设计姿势调整(重要):**

1. 内核数据结构面向 `serde_json::Value` 设计,不要试图泛型化整个 state;
2. trait object(`Arc<dyn NodeExecutor>`)是节点抽象的正确形态,接受运行时分发的少量开销;
3. 依赖清单:MCP → `modelcontextprotocol/rust-sdk`;HTTP → `reqwest`;序列化 → `serde`/`serde_json`/`serde_yaml`;异步 → `tokio`;SQLite → `rusqlite`(bundled);Schema 校验 → `jsonschema` crate;CLI → `clap`;错误处理 → `thiserror`(内核)/`anyhow`(边缘)。


### 8.1.2 "TypeScript 是否才是综合最优"的辨析

针对两个具体质疑的完整回答。

**质疑一:动态异构数据建模,TS/Python 是否更合适?——便利属实,但成本被转嫁而非消除。**

- TS/Python 处理开放集合异构数据的**语法成本**确实最低,这是事实;LangGraph 选择 Python/TS 双实现也侧面印证了该领域与动态语言的亲和性。
- 但边界校验纪律是语言无关的:无论用什么语言,节点契约都必须有 JSON Schema(或 zod/pydantic)校验,否则系统不成立。TS/Python 并没有省掉这一步,只是让**跳过它**变得更容易——这恰恰是风险。
- 关键在维度耦合:这个项目的核心资产是**可回放、可审计的状态**(checkpoint/事件溯源)。状态 schema 漂移(旧 checkpoint 与新代码不兼容)是该内核最坏的一类 bug,而动态类型语言恰恰在这个点上提供的保护最少——问题延迟到运行时、甚至延迟到"恢复一个月前的 checkpoint"时才爆炸。Rust 在节点建模上收的"税",在状态核心上会连本带利返还。
- 一句话:TS/Python 赢的是"写的时候爽",输的是"错的时候晚"。对内核而言后者权重更高。

**质疑二:异步心智,TS 是否比 Go 还方便?——语法级属实,语义级不成立。**

| 维度                          | TypeScript                                      | Go                                     | Rust/tokio         |
| --------------------------- | ----------------------------------------------- | -------------------------------------- | ------------------ |
| 顺序异步代码语法                    | **最优雅**(async/await 原生)                         | 无异步语法,代码即同步形态                          | 最繁琐                |
| 简单 fan-out                  | `Promise.all`,简洁                                | errgroup,简洁                            | JoinSet,繁琐         |
| **取消传播**                    | 无内建结构化并发;AbortController 手动接线,易泄漏;Promise 无内建超时 | **context 全链路透传取消/超时/截止,与每个 API 调用一体** | tokio 取消语义正确但需显式处理 |
| 预算耗尽时整棵 Graph 子树取消          | 需自建                                             | context.WithCancel 一行                  | 可做,繁琐              |
| CPU 密集(大 JSON 解析、schema 校验) | 单线程,阻塞事件循环                                      | 无此问题                                   | 无此问题               |

Agent 编排的异步难点从来不在"发起并发",而在**取消、超时、预算控制下的整树收回**——这正是 context 的设计目标。TS 的优势在语法层,Go 的优势在语义层;在 Agent Loop 的规模下(数十并发)两者都够用,但语义优势随 Graph 复杂度增长。

**"TS 综合最优"论断遗漏的成本项:**

1. **运行时类型擦除**:TS 类型只存在于编译期,运行时全靠 zod 类库手动补齐——对内核而言是"静态保护的幻觉",需要自己维持纪律;
2. **长驻进程行为**:Node 长进程的内存行为、依赖链质量参差,不如静态二进制可预测;
3. **部署形态**:Node 运行时 + node_modules,对比单二进制是实打实的运维差距;
4. **个人因素**:用户零 TS 经验且无偏好,学习成本与动机损耗均为纯负项;
5. **生态对齐是 TS 唯一的大幅领先项**(MCP 参考实现、LangGraph.js、最丰富的 LLM SDK)——但这是"生态最优",不等于"综合最优"。

**修正后的最终判断:**

- 若权重排序是"生态对齐 > 一切"→ TS 成立(LangGraph.js 的存在就是证据);
- 若权重排序是"内核长期正确性 + 个人偏好"→ **Rust 成立**(用户实际情形);
- 若权重排序是"迭代速度 + 并发语义 + 部署"→ Go 成立。
- 三者无绝对优劣,但"TS 综合最优"不成立:它是用两个维度(异构数据语法便利、异步语法便利)的局部冠军,掩盖了维度耦合(动态便利反噬状态核心)与被忽略的成本项(部署、长驻、个人适配)。

两个贯彻始终的纪律:

1. **层间只通过类型化接口通信**(Go interface),L1 换掉模型供应商、L3 增加 MCP,都不触动 L2 内核;
2. **L2 内核不含任何"智能"**——所有需要推理的决策(选边、裁决、收敛判断)都上移到 L4 由模型完成,内核只做确定性执行。这一条保证了内核可测试、可回放。

# 9. 目标校正:以"长程可靠性 + 可审计"为最高权重后的决策修订(2026-09-05 补充)

用户校正:项目第一目标是**解决长程任务**,因此内核必须稳定长时间运行、可溯源、可回放、事后可审查。此前以"迭代速度/探索节奏"为较高权重的比较结论需要修订。

### 9.1 TS/Python 出局的逻辑闭环

校正前,TS/Python 的动态便利是优点;校正后,同一特性在内核语境下反转为缺点,逻辑链完整闭合:

长程任务 → 状态生命周期以小时/天计 → 状态必须持久化并跨版本存活 → schema 漂移与运行时形状不确定成为主要故障源 → 动态类型语言在此提供保护最少 → **内核语言限定为静态编译型**。注意:出局范围仅限**内核**;TS/Python 用于外围脚本、一次性数据分析、MCP server 开发不受影响(工具本来就在进程外)。

### 9.2 Go vs Rust 在新权重下的终局比较

先把"稳定"拆成可比较的四个具体因子,避免用模糊词汇决策:

| 可靠性因子   | Go                                             | Rust                                              | 判定                                              |
| ------- | ---------------------------------------------- | ------------------------------------------------- | ----------------------------------------------- |
| 长驻内存行为  | GC 停顿亚毫秒级,对 IO 密集编排无实际影响;`runtime` 成熟          | 无 GC,行为最可预测;但 unsafe/依赖中的 unsafe 是残留风险            | 实践打平——Go GC 在此负载下不是真实问题,不应作为决策依据                |
| 缺陷拦截阶段  | 编译期拦截类型错误;nil map、数据竞态(race detector 运行期)是残留缺口 | 编译期拦截整类内存/并发缺陷;借用检查器在长生命周期状态对象上价值最大               | **Rust 优势真实存在**,尤其在事件溯源核心这种"状态对象被长期持有、多处传递"的代码上 |
| 大重构安全性  | 重构靠测试兜底                                        | 事件 schema 演进、checkpoint 迁移这类手术,编译器强制处理所有 match 分支 | Rust 优势——而这类手术在本项目中是**常态而非例外**                  |
| 复杂度诱发缺陷 | 语义表面小,代码"笨",难写出隐蔽 bug                          | 抽象能力强的反面:过度抽象本身是缺陷温床                              | Go 优势——需以纪律对冲(内核禁用宏、泛型克制、抽象层级设上限)               |

**结论:权重校正后 Rust 胜出,且与用户的个人偏好首次形成一致而非张力。** 但有一句必须说在前面的实话:**可靠性的主要来源是架构纪律而非语言**——确定性的内核边界、事件溯源、可回放测试,这些在 Go 里同样做得到。Rust 提供的是"纪律的编译器强制执行";选 Rust 的真正理由是:当维护者是单人、时间跨度以年计时,编译器强制执行比自律可靠。

### 9.3 四个架构方案的修订

**方案 B(事件溯源):从"Phase 2 可选变体"升级为"内核基础数据模型,自 Phase 0 起生效"。** 这是本次唯一的原则性调整。理由:可溯源、可回放、事后审查三个需求的交集,有且仅有事件溯源一个直接答案——快照只能告诉你"现在是什么",事件流才能回答"为什么会变成这样"。落地方式不需要一步到位:

- Phase 0:原计划"结构化日志"直接改为 **append-only 事件日志**(JSONL + SQLite 索引),成本相同,但格式从第一天就是"事件"而非"日志",避免二次迁移;
- Phase 1:state 不再直接可变,改为"事件折叠产生当前状态";reducer 即折叠函数;
- Phase 2:checkpoint 重新定义为"事件流截断点 + 可选快照加速",恢复 = 加载最近快照 + 重放后续事件。

**方案 A(单体内核 + 进程外工具):不变,仍为主线。** 单二进制反而增强了可审查性的一个隐藏维度——**环境可复现**:内核版本、Graph 配置哈希、模型 ID 与采样参数全部钉入事件头,一年后的审查者能重建当时的执行环境。

**方案 C(Temporal 类引擎):评分上调,但仍不推荐,需记录原因。** 上调原因:Temporal 的 workflow history 本质就是"带确定性重放校验的事件溯源",它的全部价值主张正是本项目校正后的核心需求;且 sdk-core 本身是 Rust 编写。仍不推荐的原因有二:① 它的 determinism 约束要求 workflow 代码严格确定性,LLM 调用必须全部包成 activity,Graph 的灵活路由语义要迁就引擎模型,内核就不再是"自己的";② 单机个人项目用 Temporal 等于自带一个分布式系统的运维面。**但 C 提供了一个必须吸收的纪律**(见 9.4),这正是 Temporal 架构正确的部分。

**方案 D(分布式 worker):进一步降级。** 长程可靠性目标下,分布式引入的网络分区、时钟、部分失败全是审查性的敌人。除非出现真实多机负载,永久搁置。

### 9.4 新增的第三条设计纪律(写入内核宪法)

前两条纪律(层间接口隔离、内核不含智能)之外,新增:

**3. 确定性边界:一切非确定性来源(LLM 响应、工具 IO、时钟、随机数)只能以"已记录事件"的形式进入内核。** 内核重放事件流时必须逐比特确定——这是"回放"成立的充要条件,也是 Temporal 架构的核心洞见。

由此必须区分两种"回放"语义,需求文档和测试都要分开写:

| 语义       | 定义                      | 确定性                   | 用途           |
| -------- | ----------------------- | --------------------- | ------------ |
| **审计回放** | 从事件流重建任一时刻状态与决策依据,不重新执行 | 完全确定                  | 事后审查、调试、时间旅行 |
| **断点续跑** | 从最近 checkpoint 继续真实执行   | 不保证(LLM 非确定性),但起点状态确定 | 崩溃恢复、挂起后恢复   |

配套要求:每个事件头携带 `kernel_version` / `graph_hash` / `model_id` / `model_params` / `recorded_at`;黄金回放测试(录制事件流 → 重放 → 状态逐字段比对)纳入 CI 作为内核回归门禁。

## 10. 竞品对照:DeepSeek Harness 是否已实现本项目目标(2026-09-06 补充)

### 10.1 DSH 是什么

DeepSeek Harness(2026-08-13 开源,MIT,TypeScript/Node,`npx @deepseek-ai/dsh web`):基于 **Cordis** 插件框架(源自 Koishi 聊天机器人框架生态)的 Agent 运行时,核心理念 "everything is a plugin"——模型适配器、工具注册表、会话日志、沙箱、存储、调度、**Agent Loop 本身**、UI 全部是插件,经 Profile/Bundle/Patch 三层 YAML 配置组合,不改源码即可替换任一能力。当前为开发者预览(rc 阶段,官方明示存在破坏性变更)。

关键技术事实:

- **Cordis 内核**:插件 = Fiber(六态生命周期状态机)+ `inject` 依赖声明(依赖未就绪则 PENDING,自动等待)+ `ctx.effect()` 可逆副作用(注册时即声明撤销方式,卸载按 LIFO 级联逆转,失败原子性);支持 HMR 热替换;
- **会话日志即唯一事实来源**:append-only 事件流,"model-visible means logged"(凡模型可见的内容必须能从日志重建);**resume / fork / search / replay 共享同一事件流**,Trajectory 视图按来源检视;
- 工具执行管线:pre-execute(权限/审批/沙箱拦截)→ execute(超时/重试包装)→ post-execute(结果拦截改写)→ 记录,策略插件横向切入,不侵入工具实现;
- 多 Agent:subagent 调度、目标持久化、后台任务、workflows(确定性流程);MCP 接入;Web/headless 双 profile;Python SDK + ACP 协议。

### 10.2 对本项目需求的覆盖矩阵

| 本项目需求(§1.2)                            | DSH 覆盖 | 说明                                                                        |
| -------------------------------------- | ------ | ------------------------------------------------------------------------- |
| P0 Agent Loop + 有限工具 + 单/多协议           | ✅      | Loop 本身是插件;极简模式即 MVP 形态;模型适配器可换                                           |
| P0/P1 结构化事件日志                          | ✅✅     | 超出本项目 Phase 0 设计:"模型可见即可重建"的不变量 + Trajectory 检视,与本报告 §9.4 确定性边界纪律**同一思想** |
| P1 声明式配置组合                             | ✅      | Profile/Bundle/Patch 三层叠加——但组合的是**能力**,不是**控制流图**                         |
| P1 checkpoint / 恢复 / 挂起等待              | ✅      | resume/fork 内建;审批插件即 HITL 挂起                                              |
| P2 节点级模型/工具绑定                          | ⚠️ 部分  | 粒度是 profile/subagent 级,非"图节点级"声明                                          |
| P2 multi-agent 编排                      | ⚠️ 部分  | 有 subagent 调度与目标持久化;但主 Loop 自身仍执行具体任务,非"纯观测者/协调者"分层                       |
| **P1 Graph 状态机:配置定义控制流,通用任务回落默认 Loop** | ❌      | workflows 是确定性管线,不是"带 shared state + reducer 的 FSM";图状态机不是其一等抽象           |
| **P1 收敛/发散/挂起三类退出条件一等公民**              | ❌      | 有 turn 级停止条件与 goals,无"收敛判据/无进展检测"语义                                       |
| 内核 Rust / 单二进制部署                       | ❌      | TypeScript/Node,依赖 Node 运行时                                               |
| 可依赖的稳定性                                | ❌(暂时)  | rc 预览,官方明示破坏性变更;白皮书实测记录多个 rc 版依赖断裂类问题                                     |

**概括:基础设施层重合约七成(插件系统、事件溯源日志、回放/恢复、工具管线、MCP、subagent);差异化三层(Graph 状态机一等公民、收敛语义、节点级异构绑定)基本未覆盖。**

### 10.3 对本项目决策的影响

**方向验证(强信号)。** DSH 的会话日志设计与 §9.4 的确定性边界纪律是同一洞见的独立实现——"一切非确定性只以已记录事件进入、日志即事实来源、回放/恢复/分叉共享事件流"。一家头部模型厂商把 Harness(而非模型)作为 2026 年的战略产品形态("Agent = Model + Harness"),直接印证了 §3.2 的需求判断与 §9 的权重校正。

**不改决策,改参照物。** 维持"Rust 自研内核"路线,理由:① DSH 未覆盖的三个点正是本项目的存在理由;② DSH 是 TS/Node,与 §9 已定的内核语言结论冲突;③ rc 阶段的 API 不稳定性与"长程可靠性"目标直接冲突——在其上构建意味着把内核的地基交给一个明示会有破坏性变更的上游;④ 本项目的学习目标无法在"配置别人的运行时"中达成。

**从 DSH 吸收的四项设计(按价值排序):**

1. **"model-visible means logged"不变量**:比 §9.4 的表述更锋利——凡进入模型上下文的内容必须能从事件流重建,直接采用为内核宪法第四条;
2. **Cordis 的可逆 effect**:注册即声明撤销(disposer),卸载按 LIFO 级联逆转,失败原子性。该模式与 Rust 的 RAII/Drop 天然同构,应作为内核插件/工具生命周期管理的直接蓝本——这是 DSH 给本项目最大的设计礼物;
3. **工具执行三段管线**(pre-execute 策略拦截 / execute 包装 / post-execute 结果改写):比"工具白名单 + 人工确认"更结构化,Phase 4 沙箱与审批按此管线设计;
4. **配置三层叠加**(内置 Bundle → profile patch → 用户 patch,后者按 id 覆盖前者):Graph 配置与 preset 机制可复用此模式,`--dump-config` 式调试命令也是好实践。

**DSH 的正确使用姿势:** 作为日常实用的 Agent 工具 + 一手参照实现(读 Cordis 的 Fiber/effect 源码、session log  schema、Trajectory 实现),不作为本项目地基。若未来目标从"自建内核"变为"尽快拥有可定制 Agent",再评估"将 Graph 执行器实现为 dsh 的 Loop 替换插件"这条退路——该路径技术上成立(Loop 可换),但代价是接受 TS 技术栈与 rc  churn。

## 11. 竞品对照(二):OpenAI Codex 的 Rust Runtime 与本项目设计(2026-09-06 补充)

### 11.1 Codex 架构事实(截至 2026-03,v0.116/0.117-alpha,67k+ stars)

- **真正的 TS+Rust 分工**:Rust workspace(`codex-rs/`,60+ crate,占代码库 96%+)承载**全部**业务逻辑;TypeScript 只剩两层——npm 分发壳(平台检测 + 下发对应原生二进制,解决生态分发而非技术问题)和 IDE 扩展前端。**不是"TS 编排 + Rust 加速"的混合体,而是"Rust 内核 + TS 包装"**;
- **核心模型**:Thread(SQLite 持久化会话,可 resume/**fork**/archive/**rollback**,跨进程重启存活)→ Turn(一轮推理-工具往返)→ Item(turn 内细粒度事件);`RolloutRecorder` 负责事件持久化;
- **工具编排**:ToolOrchestrator 管线 = 审批检查 → 沙箱选择 → 执行 → 拒绝后带升级重试;`apply_patch` 用 Lark 形式文法解析补丁,应用前结构化校验;
- **协议层独立成 crate**:core 与全部前端(TUI/exec/app-server)经类型化 protocol 通信,app-server 暴露 JSON-RPC 供 IDE 集成——core 是可复用 library crate;
- **multi-agent 原语**:`spawn_agent / wait_agent / send_input / close_agent` 四个内建工具,层级化子代理派生;
- **MCP**:`rmcp-client` crate——**OpenAI 在生产环境使用 Rust 官方 MCP SDK**;
- **沙箱**:平台原生(macOS Seatbelt / Linux Landlock+Bubblewrap / Windows 进程隔离)+ Starlark 编写的 exec policy(策略即数据)。

### 11.2 与本项目设计的对照

| 本项目决策(§8/§9) | Codex 对应 | 判定 |
|--------------------|-----------|------|
| Rust 内核 | Rust 承载全部业务逻辑,OpenAI 给出的四条理由(内存安全/无 GC/跨平台单二进制/OS 原语沙箱)与 §9.2 分析一致 | **强力验证** |
| append-only 事件日志 + resume/fork | Thread + RolloutRecorder:事件持久化、resume/fork/rollback 全部内建 | **强力验证**——且证明了该模式在百万级用户规模下成立 |
| 分层纪律:层间类型化接口 | protocol crate 独立,core 为 library crate,四个前端共用 | **验证**——且给出具体形态:协议独立成 crate 并版本化 |
| 内核不含智能 | ToolOrchestrator 管线是确定性代码(审批/沙箱/重试),智能全在模型 | 验证 |
| Rust MCP Tier 2 风险(§8.1.1 缺点 1) | OpenAI 用 rmcp-client 上生产 | **风险大幅缓释**:Tier 2 的维护滞后问题,头部厂商用脚投了票 |
| Graph 状态机一等公民 | ❌ 仍是 turn-based 单 Loop,无声明式控制流图 | 未覆盖——差异化仍在 |
| 收敛/发散/挂起退出语义 | ❌ 无收敛判据;rollback 是人工操作而非系统判据 | 未覆盖 |
| 节点级异构模型绑定 | ❌ 模型路由是 provider 配置级(gpt-5.3-codex 主 + mini 跑后台任务),非图节点级 | 未覆盖 |
| 主 Agent 纯观测者 | ⚠️ spawn_agent 是"工具式派生",主代理仍亲自干活 | 部分 |

**结论:Codex 是本项目技术路线(Rust 内核 + 事件溯源 + 分层协议)最接近的生产级先例,参考价值高于 DSH 的"架构理念"层面——因为它是同语言、同数据模型、可逐文件阅读的工程实现;但它依然是"单 Loop 编码 Agent",三个差异化点一个都没碰。**

### 11.3 从 Codex 吸收的具体资产(按优先级)

1. **`RolloutRecorder` + Thread 的 SQLite schema 设计**:事件表结构、fork/rollback 的存储实现——Phase 2 动手前先读 `codex-rs/core/src/` 下 rollout 相关代码,可能省掉一轮 schema 返工;
2. **ToolOrchestrator 管线**:"审批 → 沙箱选择 → 执行 → 拒绝后升级重试"四段,与 DSH 的三段管线(pre/execute/post)互为印证——两条独立实现收敛到同一形态,说明这就是工具管线的正确抽象,直接采用;
3. **exec policy 用 Starlark(策略即数据)**:与"Graph 配置即数据"同哲学;Phase 4 沙箱策略不硬编码,用嵌入式规则语言(Rust 侧有 starlark crate,Meta 出品);
4. **protocol crate 独立 + core 为 library crate**:分层纪律的具体工程形态——协议类型单独 crate 化并版本化,内核不依赖任何前端;
5. **`apply_patch` 的形式文法校验**:节点输出 schema 校验的先例——模型产出先过确定性校验再落地,正是"约束模型输出"的手段;
6. **多前端共用内核**(TUI/exec/app-server/IDE):Phase 4 之后做 UI 时,这个结构已被验证。

## 12. 全市场扫描:三个差异化点的现有实现与可参考资产(2026-09-06 补充)

对三个差异化点 + 关键支撑能力逐项扫描市面 Agent 系统后的结论。

### 12.1 "观测者主 Agent + 发散检测" → Magentic-One(最接近的已实现系统)

微软研究院 2024 年发布(基于 AutoGen,论文 arXiv:2411.04468,GAIA/AssistantBench/WebArena 三基准验证 + 消融实验),是本设想中"主 Agent 作为观测者/协调者 + 发散退出"的**唯一直接先例**:

- **双循环结构**:外循环维护 **task ledger**(事实/待查/推测/计划),内循环维护 **progress ledger**(进度/分工);内循环每轮回答五个诊断问题:任务完成了吗?团队在循环重复吗?有前进吗?下一个谁上?给什么指令?
- **停滞计数器(stall counter)**:检测到循环或无进展则计数 +1,超阈值(实验取 ≤2)则跳出内循环 → 外循环反思 → 更新账本 → 重新规划——把"恢复"建模为**状态迁移而非 prompt 自省**,论文原话:"reliable agency requires a deterministic state machine to govern the probabilistic reasoning of the LLM";
- **能力/动作分层**:Orchestrator 只选"能力"(派哪个 agent),agent 自己选"动作"(用哪个工具)——工具使用的层级化,降低主 Agent 决策空间;
- **异构模型**:Orchestrator 用重推理模型,subAgent 可用小模型(账本充当异构模型间的标准化接口);
- 消融结论:简化账本系统会导致性能显著下降——**结构化状态跟踪不是装饰,是性能来源**。

**与你的设计的差距(即剩余空间):** 账本是自然语言而非类型化 FSM;停滞判定由 LLM 回答( progress ledger 五问是问模型的),不是对 state diff 的**可计算**检测;图结构隐含在 plan 里,不是配置声明的。**你的"可计算收敛/发散判据 + 声明式图"恰好是 Magentic-One 的下一步。**

### 12.2 事件溯源内核 + Stuck Detection → OpenHands(SDK 架构最对位的参照)

OpenHands V1(2025-11 起,arXiv:2511.03690,SWE-Bench Verified ~77%,MIT,Python):

- **内核形状与你 §9 的设计几乎一致**:无状态 Agent(不可变 Pydantic 模型,纯函数 history→Action)+ Conversation(系统内**唯一**可变物,持有 append-only 类型化 EventLog)+ Workspace 抽象(Local/Docker/Remote 三种实现可互换,同一份 Agent 代码);"状态不在 Agent,而在事件";`metadata.json + events.jsonl` 恢复,可暂停/恢复/分叉/重放;
- **内建 Stuck Detector + Critic + Condenser**(上下文压缩)——发散检测作为一等组件存在;
- **V1 四条设计原则(可直接抄)**:① 隔离是可选的,不是强制沙箱(默认同进程,Docker 只是换一种 Workspace);② 无状态组件 + 单一事实来源;③ SDK 永不 import 应用层(CLI/GUI/集成都是 SDK 的消费者);④ 两层可组合(包级换 Workspace,组件级换工具/prompt/condenser/LLM);
- **V0 的教训同样值钱**:140+ 配置字段、15 个配置类, V1 全部塌缩——配置克制的反面教材;
- **"Code is the universal action"**:不做 20 个专用工具,只给 bash+python+文件编辑+浏览器四个通用工具,让模型自己组合——工具集设计的重要反直觉经验。

差距:仍是单 Loop 编码 Agent,无声明式图;Stuck Detector 是单 Agent 循环启发式,非状态机收敛语义;Python 栈。

### 12.3 "挂起等待外部输入" → Restate(工业级语义参照)

durable execution 引擎(Rust 编写,单二进制,可自托管),其三个**持久协调原语**精确对应"暂存状态机等待外部输入"的语义谱系:

| 原语 | 语义 | 对应你的场景 |
|------|------|--------------|
| Signal | 按 invocation ID 定向、可多次投递的持久信号 | 运行中纠偏(steering)、持续人工反馈 |
| Awakeable | 一次性 promise,唯一 ID,外部系统经 HTTP resolve/reject | 审批挂起:发审批请求→挂起(释放计算资源)→人审批→恢复 |
| Workflow promise | 同 workflow 内跨 handler 协调 | 节点间等待 |

三者都**跨崩溃存活**、等待时可真正挂起(不占资源)。设计你的"挂起"语义时,这张三原语表就是需求清单——不需要 Restate 本身,但其语义分类是成熟答案。Restate 的 journal replay 也是 §9.4 确定性边界的同构实现。

### 12.4 节点级异构模型绑定 → 低代码平台已产品化(但被忽视的证据)

Dify / Coze(字节)/ n8n 等低代码工作流平台中,**每个 LLM 节点独立选模型**是标配能力——证明"节点级模型绑定"有真实需求且已产品化;Codex 的"主模型 + mini 跑后台任务"是配置级版本;Magentic-One 是 agent 级版本。但这些平台全是 **DAG 工作流**(无环、无共享状态收敛),LangGraph 是代码优先——**"声明式 + 有环 FSM + 收敛判据"的组合依然无人占据。**

### 12.6 扫描后的差异化定位修正

"三个差异化点无人占据"的表述需要精确化:

1. **Graph 状态机一等公民(声明式、有环、配置定义)**:LangGraph 有环但代码优先;低代码平台声明式但无环无收敛——**组合空缺,成立**;
2. **收敛/发散判据**:Magentic-One 有停滞检测(LLM 判定、自然语言账本),OpenHands 有 stuck detector(单 Loop 启发式)——**"可计算的、作为状态机迁移条件的一等判据"空缺,成立但边界收窄**;
3. **节点级异构绑定**:低代码平台已产品化(但限 DAG)——**在"状态机图"语境下空缺,成立**。

结论不变但更扎实:三个点各自都有近似实现可以参考甚至追赶,**三者与"Rust 事件溯源内核"的组合仍然是空地**;且参考资产已经足够丰富——每个组件都有至少一个可精读的一手实现,剩下的工作是组合与可计算化,不是从零发明。
