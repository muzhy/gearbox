# 分支重执行与外部状态设计

> 状态：待定设计。本文记录候选原则和未决问题，不表示 Runtime 已支持回滚、快照或重执行。
>
> 本文只讨论从旧分支点实际发起新执行时，如何处理已经改变的工作区、数据库和外部服务。分支创建与历史继承见[会话分支设计](session-branching.md)，检查点粒度见[会话检查点设计](session-checkpoints.md)，项目总体定位见[gearbox 定位](../gearbox-positioning.md)。

## 1. 核心问题与候选原则

历史分叉只复制逻辑上的任务上下文，不会自动撤销原方案已经产生的外部效果。一次任务可能同时改变会话历史、工作区、数据库和远程服务；从旧点重执行前，必须决定新分支在哪个环境状态上运行。

候选原则是：**优先在独立环境中重执行，保留原分支及其状态。** 新建会话分支不自动回滚原方案使用的共享工作区。若只能使用同一环境，必须先保存和核对现状，再由显式操作确认恢复范围与后果；是否允许这种模式仍待定。

重新调用模型或工具也不保证得到过去的结果。模型输出、网络服务和外部数据可能变化；旧事件可以作为当时的审计证据，但新的调用必须使用新的身份、费用记录和副作用记录，不能伪装成原调用的继续。

## 2. 术语

| 操作 | 含义 | 对已有分支或外部世界的影响 |
| --- | --- | --- |
| 历史分叉 | 共享分叉点之前的记录，为新方案追加独立历史 | 不撤销既有操作 |
| 环境复制 | 为新分支构造与分叉点相符的独立文件、数据库或资源状态 | 可保留原方案继续运行，但依赖资源可复制 |
| 回滚 | 把某个受控资源恢复到旧状态 | 改变该资源当前状态，不等于撤销所有外部效果 |
| 重执行 | 从选定状态发起新的模型与工具操作，形成新尝试 | 产生新的调用身份、费用和可能的新副作用 |

## 3. 分叉点需要关联的状态

检查点不能只保存消息位置。至少需要关联以下状态，或明确标注无法恢复的部分：

- **会话与工作流**：当前分支、Node 执行位置、待处理模型或工具调用、配置和插件版本、预算消耗及上下文引用；
- **本地工作区**：已跟踪与未跟踪文件、文件元数据、配置以及所依赖的构建或运行环境；只保存 Git commit 不一定足够；
- **受控数据**：数据库、对象存储、缓存或容器状态，以及可用的事务、快照和隔离范围；
- **外部效果**：远程 API、部署、邮件、支付、用户或其他系统的操作及回执，其中一部分无法还原；
- **外部观察**：检索结果、时间相关数据和其他只读观察。旧响应可作为当时证据，重执行时外部世界可能已经变化。

检查点可以引用独立的状态清单或快照，不要求把所有内容复制进会话事件。若状态范围未知，就不能据此宣称分支可从过去精确重执行。

## 4. 按资源选择策略

| 场景 | 可考虑的策略 | 主要边界 |
| --- | --- | --- |
| Git 管理的代码 | 记录基线提交和工作区改动，为新分支创建独立 worktree 或目录 | Git 不覆盖未捕获的未跟踪文件、数据库、进程和远程操作；共享构建产物也可能互相影响 |
| 普通文本或文件集合 | 内容版本、目录快照或复制到独立工作区 | 还需保留路径、元数据、附件及外部引用；大文件复制成本待评估 |
| 数据库任务 | 事务回滚、测试库、数据库快照或临时实例 | 已提交事务的外部消费者、跨库写入及消息队列不一定能同步回滚 |
| 容器或可重建服务 | 从镜像与配置新建隔离实例，必要时恢复数据卷 | 镜像、依赖、密钥和外部连接必须匹配；容器快照不覆盖外部服务 |
| 只读外部查询 | 保存旧响应作为证据；重执行时明确选择使用旧证据或重新查询 | 重新查询可能返回不同结果；旧响应只代表当时观察 |
| 可补偿的远程操作 | 保留回执并执行业务定义的补偿动作，再从当前状态继续 | 补偿是新操作，可能失败或不完整，不能称为精确回滚 |
| 邮件、付款、发布和真实设备操作 | 尽量在操作前完成分叉和验证；必要时使用模拟或测试环境 | 操作后通常不能恢复到原分叉点，应从当前现实状态发起新任务 |
| 超时或结果未知的调用 | 先按调用身份查询、对账或人工核对实际效果 | 结果未明时不能盲目重试，也不能假设没有副作用 |

## 5. 从旧点重执行的候选流程

1. **核对分叉点**：检查会话、工作流、待处理调用和必要产物是否完整，确认没有结果未知的在途操作。
2. **盘点后续效果**：找出分叉点之后在文件、数据、远程资源和用户操作中已经发生的改变，并标出无法确认的部分。
3. **逐项选择策略**：对每项资源选择复制、从快照恢复到独立环境、重新构建、补偿、只读复查，或声明无法重执行。不能因其中一项资源可回滚就认为整个任务可回滚。
4. **建立新环境**：关联具体版本或快照，核对实际环境与分叉点要求一致；原分支的记录与环境保持可追溯。
5. **以新身份继续**：新模型请求、工具调用和费用记入新分支；旧历史作为祖先引用，不覆盖或重新标记旧操作。

若任一关键资源无法恢复或隔离，可保留仅供查看的历史分支，也可从当前真实状态启动带来源说明的新尝试；后者不能称为“从旧分叉点重执行”。

## 6. Runtime 与插件需要表达的能力

Runtime 负责关联会话检查点和环境状态，判断分支是否具备实际执行条件；具体文件、数据库或外部服务的复制、恢复和核对能力由相应工具或插件提供。候选契约至少应表达：

- 本次操作读写哪些资源以及是否有副作用；
- 是否有可查询的调用身份；
- 是否支持快照、隔离、恢复或补偿；
- 结果未知时怎样核对；
- 实际执行后的资源版本和结果如何记录。

这些声明不能单独证明状态正确。能力未知、声明与实际不符或关键资源无法核对时，检查点先作为历史查看点，不自动开放从过去状态重执行。插件也不能用简单的“可回滚”标志掩盖跨系统副作用。

## 7. 待决策问题

1. 首个试点支持哪些资源范围：只覆盖 Git 工作区，还是同时要求文件快照、数据库及远程调用？
2. 环境状态清单由 Runtime 自动收集、由插件声明，还是两者结合；如何发现插件未声明的副作用？
3. 快照何时创建、如何清理和验证；缺少分叉前快照时是否允许按构建配方重建近似环境？
4. 是否允许恢复共享环境；若允许，如何避免破坏仍在使用它的原分支或其他任务？
5. 补偿操作的失败、部分成功和重复执行怎样记入历史；是否需要人工判断才能继续？
6. 对不可恢复的外部世界，用户能否选择从当前状态派生新任务，以及界面如何避免把它误认作精确重执行？
