# 会话检查点设计

> 状态：设计草案，尚未实现。
>
> 本文只决定会话执行记录与检查点的恢复粒度。会话分支的用户语义见[会话分支设计](session-branching.md)；从旧点实际重新执行时的外部状态见[分支重执行与外部状态设计](branch-reexecution.md)。项目总体定位见[gearbox 定位](../gearbox-positioning.md)。

## 1. 决策

Runtime 同时记录事件和检查点，但两者不承担相同职责：

- 每次模型调用和工具调用都记录开始、结束及结果事件，事件按实际发生顺序保存。
- 每次调用完成后建立机器可恢复的调用检查点。检查点可以引用事件和状态增量，不要求复制完整会话或工作区。
- 当产物、判断或路由形成了稳定且可理解的任务状态时，在调用检查点上标记语义检查点。语义检查点才是默认适合展示给用户的候选位置；并非每个调用检查点都需要成为用户可见的分叉点。
- 调用仍在进行、模型响应未到达或工具仍在执行时，不把该位置当作可继续的检查点。需要恢复时，应从最近一个已完成且状态可重建的检查点开始。

这样既能在调用级别恢复，又不会把每一个内部事件都误当成有独立意义的任务阶段。分支是否开放以及如何继承检查点，由[会话分支设计](session-branching.md)规定。

## 2. 术语边界

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 工作流 Node | 用户配置的执行单元 | “修改代码”或“运行检查” |
| 历史事件 | 已发生的一项操作或结果 | 模型请求、模型响应、工具调用、工具结果、路由决定 |
| 调用检查点 | 一次调用完成后可供 Runtime 重建的机器状态 | 模型响应已记录、工具结果已提交 |
| 语义检查点 | 产物、判断或路由已经形成的稳定状态 | Agent Loop 提交候选修改、Control Node 得出测试结论 |

一个工作流 Node 可以执行多次，每次执行有独立身份；一次执行也可以产生多个事件和检查点。因此不能用 Node 名称或单次模型调用代表整段会话历史。

## 3. Agent Loop 内的记录顺序

模型请求及响应视为一次模型调用，工具派发及每个工具结果视为独立的工具调用。每项调用都保留开始和结束事件，并在完成时建立检查点。模型一次响应请求多个工具时，按协议顺序处理，并为待处理队列的变化建立检查点：

```text
P0：进入“修改代码” Agent Loop Node
    模型请求 #1 → 模型响应 #1，请求工具 A、B
P1：模型调用 #1 完成；待处理 A、B
    工具 A 调用 → 结果
P2：工具 A 完成；待处理 B
    工具 B 调用 → 结果
P3：工具 B 完成；本批工具已结清
    模型请求 #2 → 模型响应 #2，形成最终产物
P4：模型调用 #2 完成
P5：Agent Loop Node 完成
    Control Node 执行检查并记录路由结果
P6：Control Node 完成
```

`P1`、`P2` 和 `P3` 是调用检查点；它们通常只供恢复和审计使用。形成候选产物、阶段性提交或检查结论时，Runtime 可以在相应检查点上标记语义检查点。展示层可以把内部调用折叠为 Node 摘要，再展开事件和检查点；展示方式不改变底层记录粒度。

如果分叉或恢复发生在工具 A 完成后，工具 B 仍是待处理队列的一部分。除非执行了明确的取消或重新规划操作，不能静默丢弃这类协议状态；这类操作的分支语义见[会话分支设计](session-branching.md)。

## 4. 检查点必须能定位的状态

一个允许继续执行的检查点至少应能定位或重建：

- 当前会话分支、工作流位置和所在 Node 的局部进度；
- 已完成调用、待处理模型响应或工具队列，以及各调用身份；
- 有效配置、模型与插件版本；
- 剩余的模型、工具、时间和其他预算；
- 继续请求所需的上下文资料和关键产物引用；
- 适用时的工作区、数据库和其他外部资源状态引用。

检查点可以引用已经记录的事件、快照或状态清单来重建这些内容。若关键状态无法定位，只能作为历史查看点，不能宣称可以从该处可靠继续。外部资源的复制、恢复和核对不由本文件决定，见[分支重执行与外部状态设计](branch-reexecution.md)。

## 5. 插件报告契约

Runtime 统一分配事件和检查点身份。用户自定义 Agent Loop Node 应报告每次模型请求、响应、工具调用、工具结果及剩余待处理操作；Control Node 应报告检查操作、结果和路由决定。插件不能私下维护一份与 Runtime 会话历史脱节的权威记录。

如果插件内部操作无法逐项报告，Runtime 只能把它作为不透明执行单元记录，最细检查点退化到该 Node 完成处。这是明确的能力限制，而不是假装可以在插件内部恢复或分叉。插件何时主动标记语义检查点、以及 Runtime 是否能依据结构化产物辅助识别，仍需在插件接口设计中确定。
