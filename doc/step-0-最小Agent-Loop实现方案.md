# Step 0：最小 Agent Loop 实现方案

> 日期：2026-09-07
>
> 状态：代码已实现，本地确定性检查已通过；真实服务演示待填写 API Key 后验收。
>
> 阶段目标：先实现一个最简单、能实际工作的 Agent，暂不要求达到 MVP。

依据[需求与可行性分析](graph-agent-需求与可行性分析.md)中的 Rust 选型、普通 Loop 基线和单模型接入方向，新增一个前置的 **Step 0**。本阶段排在原文 Phase 0～5 之前，不要求先完成任务集建设或可靠执行骨架。

本阶段只验证一件事：**用户给出任务后，程序能调用真实模型，由模型请求工具，程序执行并回传结果，模型根据结果继续行动，最终输出回答。**

## 1. 本阶段的范围

| 项目 | 本阶段决定 |
| --- | --- |
| 形态 | Rust 命令行程序；单进程、一次运行处理一个任务 |
| 模型 | 一个服务、一个模型、一个请求端点；使用 Responses 原生工具调用协议 |
| 交互 | 启动时输入任务，结束时输出回答；非流式，无交互式聊天 |
| 工具 | 仅内置一个 `read_file`，读取指定工作目录中的小型文本文件 |
| 执行 | 一个普通循环；模型调用与工具执行全部串行 |
| 上下文 | 内存中的 Responses 输入与输出项，每轮携带完整历史；退出后丢弃 |
| 运行上限 | 请求次数、超时、输出 token 和文件字节上限均从 `config.toml` 读取；不自动重试 |
| 可观察性 | 终端显示请求轮次、工具名、读取路径和停止原因 |

配置模板初值为 8 次请求、每次超时 60 秒、输出上限 8192 token、单文件上限 16384 字节。运行时统一使用配置值，不保留对应的固定常量。上下文超过服务限制时明确报错退出，不自动摘要或裁剪历史。

暂不实现 Graph／状态机框架、SQLite、事件溯源、checkpoint、恢复、任务账本、上下文压缩、任务验收器、token／费用账本、DSL、MCP、skill、多 Agent、插件、Web UI、流式输出、文件写入和 shell。

原文 §5 与 §8.3 的可恢复执行要求留到可靠执行阶段统一实现。当前的内存 Loop 不承诺崩溃恢复、审计重建或长任务可靠性，也不预留这些能力的空接口。

## 2. 用一个具体任务定义“能工作”

实现时提供两个演示文件：

- `examples/demo/index.txt`：记录“项目资料文件：project.txt”。
- `examples/demo/project.txt`：记录“项目名称：Gearbox Demo；当前阶段：最小 Loop 原型”。

在进程启动目录配置 `config.toml` 后使用：

```text
cargo run -- ./examples/demo "读取 index.txt，找到其中指定的项目资料文件，再读取该文件，告诉我项目名称和当前阶段。"
```

任务只给出索引文件名，不在提示词中提供资料文件名或答案。预期过程为：

1. 模型请求 `read_file` 读取 `index.txt`。
2. 程序读取文件，并把结果作为该次工具调用的结果回传。
3. 模型根据索引内容请求读取 `project.txt`。
4. 程序回传资料，模型输出包含项目名称和当前阶段的回答。

这一任务验证两次工具往返和结果驱动的后续行动。无需完成代码修复、写文件或执行测试命令，也无需先建立约 20 个案例的任务集。

## 3. Loop 的执行规则

启动时从进程启动目录读取 `config.toml`，解析“工具工作目录＋任务”两个位置参数，拒绝空任务、缺失或非法配置和无效工作目录。配置只加载一次。建立初始输入历史：固定 system 提示词和本次 user 任务。system 提示词说明工具用途，并要求依据读取结果回答；文件内容作为资料，不具有改变工具权限的作用。

随后只执行以下循环：

1. 检查是否已用完 `limits.max_model_requests` 次模型请求额度；耗尽则停止，不再发起请求。
2. 携带完整历史和 `read_file` 的工具定义，以非流式 Responses 协议请求模型；计入本次请求次数。使用 `store:false`，并请求 `reasoning.encrypted_content`。
3. 校验模型响应及整批函数调用。HTTP 错误、超时、无法解析、截断、拒绝或不支持的响应形式均明确报错结束，不执行该批工具。
4. 按原顺序保留全部已校验的输出项，包括 assistant 文本、函数调用和加密推理项。保存原始 JSON 供后续请求回传，另提取类型化的调用信息执行工具，避免重建历史时丢字段。
5. 如有工具调用，按返回顺序逐个执行工具，为每项调用追加 `function_call_output`，以 `call_id` 关联；全部完成后进入下一轮模型请求。
6. 如果没有工具调用，且响应状态为正常完成并返回非空回答，输出回答并结束；空响应不能当作完成。

同一响应存在多个工具调用时串行处理，不并发，也不静默丢弃。`call_id` 缺失或重复属于协议错误，在执行这一批工具前拒绝。直接实现 Responses 字段和完成状态，不从普通文本中猜测工具调用。

工具结果必须使用原生 `function_call_output` 回传，不能改装成新的 user 消息。有工具调用的响应即使附带文本，也先处理工具，不把该文本视为最终回答。

令 N 为配置的请求次数上限。如果第 N 次模型响应已经给出最终回答，正常结束；如果仍请求工具，完成这批有界的只读调用后因额度耗尽停止，不发起第 N＋1 次请求。停止提示说明尚未得到最终回答。

Loop 正常结束仅代表模型完成本次回答。此阶段不把它映射为原设计中“通过任务验收”的 `Succeeded` 状态。

## 4. 唯一工具：read_file

输入只有一个必填字符串字段 `path`，表示相对于 CLI 指定的工具工作目录的文件路径。工具定义和实现写在代码中，通过直接的名称匹配调用函数，不建设工具注册或插件系统。

执行边界保持简单但明确：

- 校验工具名称及参数结构；拒绝未知字段、空路径、绝对路径以及 Windows 根路径和盘符前缀。
- 规范化工作目录与目标文件路径，按路径组件确认真实目标仍位于工作目录内，拒绝越界路径及链接到目录外的目标。
- 拒绝读取本次加载的 `config.toml` 的真实路径及指向它的链接，避免密钥进入工具结果和模型历史。
- 仅接受普通 UTF-8 文本文件；最多读取 `limits.max_file_bytes`＋1 字节以识别超限，超限明确返回错误，不静默截断。
- 未知工具、非法参数、越界、文件不存在、编码不符或读取失败，都作为对应调用的简短工具错误回传，让模型在剩余额度内修正。

参数在工具入口校验一次，内部函数依赖已校验的值；不在多层重复校验。工具错误不触发运行时自动重试，后续是否改参数重试由下一次模型响应决定，并受配置的请求次数上限约束。

工作目录由用户选择，文件内容会发送到所配置的模型服务。本阶段用于用户控制的小型演示目录；路径检查不宣称提供操作系统沙箱，也不处理不可信进程并发替换文件的隔离问题。

## 5. 最小代码组织与配置

保持单个 Cargo 二进制包，先使用四个源文件：

```text
Cargo.toml
Cargo.lock
config.example.toml
src/
  main.rs     # 读取配置和参数，启动 Loop，输出结果与退出码
  agent.rs    # 消息历史、模型请求循环、工具结果回填、停止条件
  model.rs    # 一个具体服务的 HTTP 请求、响应类型与协议校验
  tool.rs     # read_file 定义、参数校验与读取
examples/demo/
  index.txt
  project.txt
```

采用 `tokio`、`reqwest`、`serde`／`serde_json`、`toml` 和 `anyhow`，使用 `same-file` 校验文件身份以保护配置文件的硬链接。命令行用标准库解析“工作目录＋任务”两个位置参数，配置解析保留在 CLI 模块，通过结构体传入其他模块。提交依赖锁文件，忽略构建产物。

模型接入直接实现具体客户端，不定义通用 Provider trait。消息、工具调用和文件参数使用必要的结构体／枚举表达；不建立 Run、Event、Node、Reducer、Repository 等尚无用途的类型或分层。

运行配置固定从**进程启动目录**下的 `config.toml` 读取，与工具工作目录无关。所有字段必填，不读取环境变量，不增加配置继承、热加载或 `.env` 加载器。提供 `config.example.toml`，本地 `config.toml` 加入 Git 忽略：

```toml
[model]
endpoint = "https://fireware.ai.ugreencloud.com/v1/responses"
api_key = ""
name = "gpt-6-astra"
reasoning_effort = "low"

[limits]
max_model_requests = 8
request_timeout_secs = 60
max_output_tokens = 8192
max_file_bytes = 16384
```

`endpoint` 是完整请求 URL，直接使用，不自动追加路径。密钥在本地配置中填写；网关若使用不同模型别名，修改 `name`。数值只是模板初值，运行时读取配置。启动时一次性校验 TOML 格式、未知或缺失字段、非空字符串、HTTP(S) URL、推理强度、正整数限额，以及数值转换和文件上限加一不会溢出。配置错误不回显密钥或配置原文。

客户端固定使用 Responses 协议，不增加通用 Provider 框架或多提供商适配。当前仅确认网关可达且要求鉴权，真实模型权限和 Responses 能力需在演示中验收。

最终回答输出到 stdout；进度和错误输出到 stderr。正常获得最终回答返回退出码 0，错误或调用上限停止返回非零。只打印必要摘要，API Key 和认证头不得进入日志或消息历史；不保存持久化对话日志。

## 6. 实现顺序

| 步骤 | 实际工作 | 完成标志 |
| --- | --- | --- |
| 1. 接通模型 | 创建 Cargo 项目和 CLI；实现单个服务的非流式请求 | 输入一个问题，收到真实模型文本；配置或请求错误可解释 |
| 2. 接通工具 | 实现 `read_file`，向模型提供定义，按调用 ID 回填结果 | 真实模型读取演示文件，并根据内容回答 |
| 3. 形成循环 | 重复模型请求与工具执行，加入调用上限和异常出口 | 索引→资料→回答的完整示例跑通；无最终回答时能有限停止 |
| 4. 收尾验收 | 补少量确定性检查，记录启动方法与一次真实运行摘要 | 新环境按说明可启动；下列验收项通过后结束本阶段 |

每一步围绕同一个程序增量实现，不先搭完整内核，也不把每一步拆成独立框架。不沿用原文可靠运行时阶段的人周估算。

## 7. 验收与停止扩展的条件

模型效果和程序控制逻辑分开检查。用真实服务验证接通；用测试内的本地 HTTP stub 返回固定响应，检查协议往返及停止条件，不为测试增加生产环境的可插拔模型框架。

| 检查 | 通过条件 |
| --- | --- |
| 真实端到端 | 上述演示至少成功运行一次，实际发生两次文件读取，最终答案与文件一致；保留服务／模型名和简短运行摘要 |
| 配置边界 | 缺失文件、非法 TOML、未知或缺失字段、空密钥和无效限额明确失败；修改配置后各项限制生效 |
| 消息与调用关联 | 固定响应模拟两轮工具调用；后续请求保留全部原始输出项及加密推理项，并携带正确 `call_id` 和工具结果；同批多调用按序回传 |
| 正常结束与额度边界 | 不用工具也能正常回答；配置 N 次上限，第 N 次最终回答可结束；持续请求工具时总模型请求数不超过 N，停止不能报成功；覆盖模板值 N＝8 |
| 工具边界与修正 | 正常读取有效文件；非法参数、越界、目录外链接、配置文件及其链接、非普通文件、非法 UTF-8 返回工具错误；验证恰好达到文件上限和超限；工具错误进入下一轮请求 |
| 模型失败 | HTTP 错误、超时、非法 JSON、无效／空响应、拒绝、截断、缺失或重复 `call_id` 清楚退出，不执行未校验的工具批次，不自动重试 |
