# 自建 Graph Agent：需求与可行性分析

> 初稿日期：2026-09-05  
> 修订日期：2026-09-07  
> 状态：修订后的设计基线；能力效果和工期仍需原型验证。  
> 结论：**面向单机个人使用，构建一个支持显式控制流、任务状态持久化、上下文组装及审计的 Agent 运行时，目标合理、技术上可行。保留 Rust 自研路线，但先验证恢复正确性和实际任务收益，再扩大到多 Agent 与生态能力。**

> 当前实施起点（2026-09-07）：按最新范围要求，先完成 [Step 0：最小 Agent Loop 实现方案](step-0-最小Agent-Loop实现方案.md)，仅验证真实模型与只读工具的内存循环可以工作，不要求达到 MVP。本文件 Phase 0～5 作为后续路线参考，其中任务集、持久化、恢复及其他可靠运行时要求不作为 Step 0 的前置条件或验收项。

本版将原文分散在技术选型、目标校正和竞品补充中的结论合并为一套当前决策。历史讨论中的“Go 优先”“TS/Python 不适合作为长期内核”“三个差异化点无人占据”等表述不再作为实施依据。既有 Rust 偏好和长期学习目标保留；本版新增的试点范围、容量和工期数字均为规划假设，需要在对应阶段用证据确认。

## 0. 当前决策与立项依据

| 事项 | 当前结论 | 成立条件或边界 |
| --- | --- | --- |
| 项目定位 | 个人长期使用与系统工程学习并重 | 自研价值不以市场空白为前提；商业需求尚未验证 |
| 第一目标 | 长任务的执行可靠性、信息连续性和可审计性 | 分项验收，不承诺任意任务都能成功 |
| 实现语言 | Rust | 依据维护者偏好、类型建模和部署需求；接受异步与生态适配成本 |
| 部署架构 | 单机、单体内核、按需调用进程外工具 | 初期每个 run 串行执行、同一 run 只有一个执行者 |
| 状态模型 | 有限控制状态＋业务数据＋有向控制流图 | 允许循环；节点不等于 FSM 状态，也不必都是 Agent |
| 持久化 | SQLite 权威事件记录＋可重建状态投影＋checkpoint | JSONL 用于导出；大内容可作为不可变产物由事件引用 |
| 决策边界 | 确定性代码执行规则，模型提供语义判断建议 | 模型建议必须记录、校验，不能绕过边和权限约束 |
| 上下文管理 | 从早期真实任务阶段加入 | 保存历史与让模型正确使用历史分别验收 |
| Graph 配置 | 执行语义验证后再稳定最小 DSL | 配置组合已安装能力；新增业务能力仍可能需要代码 |
| 多 Agent | 可选扩展 | 通过对比实验说明收益后采用，不作为内核成立的前提 |
| 差异化 | 待验证的使用体验与任务效果假设 | 不再以“声明式、有环、模型绑定的组合无人实现”立项 |

技术上可以实现，不等于小工作量。主要风险包括工具副作用与本地记录不一致、上下文遗漏、验收器失真、状态兼容性和范围扩张。成熟系统提供可参考机制，但组合后的正确性仍需本项目验证。

## 1. 目标、用户场景与范围

### 1.1 目标陈述

面向单机个人使用，在一类可验收的长任务中，通过显式控制流、持久化任务状态和按节点组装上下文，使任务能够在资源预算内执行、暂停和恢复，并保留可追溯的执行证据。

“可靠性”拆分为三个目标，避免用其中一项代替其余两项：

| 目标 | 需要改善的行为 | 不由该机制自动保证的事情 |
| --- | --- | --- |
| 执行可靠性 | 崩溃后恢复已记录进度；识别未决调用；不盲目重复危险写操作 | 外部服务永远可用、任意工具只执行一次 |
| 信息连续性 | 目标、约束、证据和待办在上下文重组后仍可访问 | 模型一定注意到或正确理解所有信息 |
| 任务质量 | 产物通过明确验收，或交由人工作出有记录的判断 | 测试通过等于不存在缺陷、格式合规等于内容正确 |

### 1.2 首轮试点

默认候选为：**固定小型代码仓库中的受限缺陷修复**，流程包含定位、修改、验证和必要的修正循环。选择它是因为结果较容易用既有测试、回归检查和人工复核共同评估。Phase 0 应检查这些任务是否来自实际需要；若不匹配，可替换为另一类有明确验收依据的任务。

首轮工具限定为受控工作目录下的读取、搜索、补丁写入和固定验证命令。执行测试代码仍然有风险，应使用隔离的实验环境；环境未就绪前使用模拟工具验证内核。开放式调研和报告写作作为后续泛化场景，其内容质量采用分项评价和人工验收，不宣称可自动证明收敛。

建议用以下尺度界定首轮“长程”，作为规划目标，不作为已经达到的指标：

- 选入需要多轮修正、通常涉及数十次模型或工具调用的真实任务；以约 20～100 次可记录调用作为早期容量探索范围，不人为拉长本来很短的任务。
- 覆盖至少两次上下文重新组装，其中包含一次历史摘要或证据按需回查。
- 覆盖执行中进程中断及重新启动，以及一次等待外部输入后恢复。
- 将活跃执行时间、等待时间和进程驻留时间分别记录。跨夜等待测试不能替代持续执行稳定性测试。
- 使用独立的模拟压力场景检查事件累计、内存和恢复耗时；模拟结果不能代替真实任务效果。

### 1.3 需求与对应机制

| 痛点 | 采用机制 | 验证方法 |
| --- | --- | --- |
| 长历史导致目标或约束遗漏 | 持久化目标账本＋上下文组装＋原始证据回查 | 压缩前后关键约束保留测试及任务结果检查 |
| 模型自由决定步骤导致流程失控 | 显式条件边、受限工具、运行时校验 | 非法路由和越权调用被拒绝并记录 |
| 输出格式或含义不符合下游要求 | JSON Schema＋业务校验器 | 结构错误与业务失败走不同处理路径 |
| 进程崩溃后重复执行或丢失进度 | 事件持久化、调用身份、checkpoint、恢复核对 | 在不同故障窗口注入中断并检查副作用 |
| 反复尝试消耗预算 | 总预算账本、进展证据、重试和重规划上限 | 恢复不重置额度；停滞与资源耗尽分别记录 |
| 分工后信息传递失真 | 节点输入视图、结构化产物和来源引用 | 下游能回查证据；多节点效果与单 Loop 基线比较 |

### 1.4 优先级

| 优先级 | 需求 | 完成阶段 |
| --- | --- | --- |
| P0 | 任务集、验收依据、普通 Agent Loop 基线 | Phase 0 |
| P0 | 串行执行、类型化事件、SQLite、调用恢复、预算、取消 | Phase 1 |
| P0 | 单模型接入、有限工具、上下文组装、真实任务修正循环 | Phase 2 |
| P1 | 最小 Graph DSL、用户等待／恢复、版本兼容策略、节点契约 | Phase 3；基本运行状态和契约接口在 Phase 1 定义 |
| P1 | 任务进展策略、异构模型效果评估、可选规划 Agent | Phase 4；基础上限和验收器在 P0 已存在 |
| P2 | MCP、skill 加载、并行 Agent、trace UI、完整沙箱和插件管理 | Phase 5，逐项由真实需求驱动 |

### 1.5 首轮不做范围

首轮不做多租户、分布式 worker、插件市场、可视化图编辑器、任意动态改图和跨所有模型服务的兼容承诺。通用进展算法、任意外部副作用的 exactly-once 保证、自动撤销所有工具操作也不属于项目承诺。

完整跨平台沙箱可以后置，但有限工具的权限、工作目录、超时、输出大小、子进程清理和恢复策略必须随工具一起实现。进程外工具与 MCP 通信都不自动构成安全隔离。

## 2. 可行性、自研价值与效果假设

### 2.1 技术可行性

| 组件            | 可行性与主要工作            | 主要验证风险                         |
| ------------- | ------------------- | ------------------------------ |
| 最小 Agent Loop | 可用现成 HTTP／SDK 接入实现  | API 错误、工具协议差异、输出截断和重试成本        |
| 串行有环图执行器      | 可实现；采用显式调度和状态迁移     | 重试、循环、等待、取消及无合法后继的语义           |
| 节点模型与工具配置     | 结构上较直接              | 服务能力不同、权限继承、上下文和预算边界           |
| 上下文组装         | 可以先从固定规则实现          | 目标遗漏、摘要误差、陈旧证据和上下文容量           |
| 持久化与恢复        | 成熟机制可参考，工程风险较高      | 工具已生效而结果未落盘、重复恢复、调用状态未知        |
| 事件回放和兼容       | 可实现                 | 缺事件、旧 schema、reducer 变化、引用产物缺失 |
| 任务验收与进展检测     | 特定任务可实现；开放式任务需要人工参与 | 验收覆盖不足、误停、指标被模型迎合              |
| 多 Agent／并行    | 技术可实现，效果需实验         | 状态合并、失败传播、信息损失、成本和取消           |
| MCP／插件        | 复用 SDK 和进程协议        | 连接、认证、版本、生命周期及权限管理             |

内核包含有环控制流，不能用拓扑排序遍历概括。完成演示只说明正常路径可执行；可靠性还需要故障、边界和旧数据恢复验证。

### 2.2 为什么仍选择自研

自研路线主要基于长期学习、个人控制需求和 Rust 偏好。它能提供对执行语义、数据模型和调试入口的直接控制，同时意味着持久化、兼容性、安全边界及维护成本由自己承担。

在 LangGraph 等已有框架上添加配置加载、节点模型选择和验收逻辑，是需要保留的替代方案。这些需求不天然要求修改框架内核。使用或扩展框架也可以学习状态机与恢复机制，不能简单等同于只学 API。

| 选择            | 适用情形                   | 本项目的处理方式                |
| ------------- | ---------------------- | ----------------------- |
| 自研 Rust 内核    | 希望长期理解并控制执行机制，愿意维护基础设施 | 当前主线；先限定单机串行子集          |
| 基于现有框架扩展      | 更关注尽早完成业务任务、复用持久化生态    | 用作效果和开发成本的参照；主线受阻时可重新选择 |
| 使用现成 Agent 产品 | 核心诉求是日常生产力             | 可以与自研并行存在，不要求自研立刻替代全部用途 |

### 2.3 差异化改为待验证假设

声明式配置、有环执行、节点模型选择和进展检测已有不同形式的实现。现有证据不足以证明这些能力的组合构成市场空白；“Rust＋事件溯源”的技术组合也不直接等于用户愿意采用的优势。

本项目优先验证三个假设：

1. 对固定任务集，显式任务状态和上下文组装能降低约束遗漏与重复工作。
2. 在明确的故障条件下，恢复操作更清楚，未知副作用能够被识别和处理。
3. 用户能以较少配置理解“当前在做什么、为什么停止、如何继续”，无需阅读大量原始日志。

多模型混用的成本收益、通用 Graph 的配置便利性和主 Agent 规划收益单独评估，不作为上述假设的默认前提。

## 3. 控制状态、验收与调度语义

### 3.1 控制与数据分离

运行时采用扩展状态机的工程思路：有限的生命周期状态承载控制语义，业务数据独立存储，Graph 定义允许的节点执行关系。避免把所有业务数据组合枚举成控制状态。

初期实现约束：

- 每个 run 串行调度，一个调度器负责状态提交；通过进程锁或等效机制阻止两个进程同时恢复同一 run。
- 节点接收受限状态视图，返回产物、状态更新建议和证据引用，不直接修改持久化共享状态。
- 运行时执行契约校验，提交事件，再由确定性 reducer 更新状态投影。
- 同一节点的重复进入、同一次逻辑操作的重试、不同业务迭代使用不同的身份字段，避免混淆。
- 并行节点的合并顺序、冲突处理与取消传播在 Phase 5 单独设计，不靠完成先后顺序隐式决定业务结果。

### 3.2 生命周期状态

| 状态 | 含义 | 后续处理 |
| --- | --- | --- |
| Created | 任务与配置已记录，尚未派发 | 启动或取消 |
| Running | 正在调度、执行或处理结果 | 继续、等待或进入终态 |
| Waiting | 等待输入、授权或工具结果核对，不继续派发 | 对应等待被有效处理后回到 Running，或明确结束 |
| Succeeded | 已满足本任务声明的验收方式 | 保留验收证据；不再派发 |
| Failed | 不可恢复错误，或允许的恢复策略已耗尽 | 记录错误；新尝试创建有来源关系的 run |
| Cancelled | 用户取消已完成处理 | 保留可能已发生的副作用及未决记录 |
| Stopped | 按策略停止，如预算耗尽或进展策略要求终止 | 保留现场；继续工作需显式创建关联 run 并说明预算策略 |

`Waiting` 是非终态。`reason` 与状态分开记录，例如 `NeedsInput`、`NeedsApproval`、`ToolOutcomeUnknown`、`BudgetExceeded`、`NoProgress`、`ValidationFailed`。进展不足可以触发重新规划或等待，不必直接变成 Stopped。

基本迁移为：Created → Running；Running → Waiting → Running；Running → Succeeded／Failed／Cancelled／Stopped。Created 和 Waiting 也允许明确取消；等待拒绝或超时可以按策略进入 Failed 或 Stopped。终态不原地改写成运行中，后续尝试保留父 run 和起点证据，防止混淆历史结论。

取消首先记录请求并停止新派发，然后处理子进程、在途调用和未决副作用。取消网络请求或丢弃异步任务，不证明远端操作已经停止。只有完成取消收尾或登记未决结果后，才记录终态及其限制。

### 3.3 验收、进展和资源限制

| 机制 | 输入与输出 | 实施原则 |
| --- | --- | --- |
| 结构校验 | 节点产物与 JSON Schema → 合规／不合规 | 只判断形状和约束，不把结构通过当作任务完成 |
| 任务验收器 | 产物、基线和验证证据 → accepted／rejected／inconclusive | 固定版本；记录结果和依据；避免模型自行改验收标准 |
| 进展检测器 | 有业务含义的变化、错误和新证据 → 指标与建议动作 | 状态 diff、节点重复只是线索，不能单独证明发散 |
| 资源限制器 | 累计调用、token、时间、成本估算 → 可继续／需停止 | 独立于任务质量和进展判断，恢复不能重置 |

不使用通用的 `Sₜ₊₁ ≈ Sₜ` 或状态距离作为任务完成条件。日志和时间戳变化不代表进展；状态稳定可能是等待或卡住。测试全部通过也只证明已执行测试覆盖的要求，仍需保留回归范围和未验证事项。

开放式任务将模型评价标记为评价意见；若声明需要人工验收，必须收到人工决定才能记为 Succeeded。记录 `acceptance_mode`，区分确定性验证、人工确认和其他已配置方式。

### 3.4 主 Agent 的角色

确定性条件直接由代码判断，例如验证失败进入修复节点。需要语义判断或重新规划时，才调用可选规划 Agent。其输入应包含目标、约束、能力说明、进度和允许动作；业务背景可以出现，重点是控制职责和权限。

模型输出是待校验建议。运行时检查动作是否合法、预算是否允许、输入是否完整后再执行，并记录建议与实际决策。主 Agent 的有效验收标准是决策合规、可追溯和效果改善，不是 prompt 中完全没有业务知识。

## 4. 上下文与证据管理

### 4.1 数据分层

| 数据 | 内容 | 使用方式 |
| --- | --- | --- |
| 任务目标与约束 | 当前目标、成功条件、禁止事项、用户更正 | 版本化保存，进入所有相关节点的上下文 |
| 任务账本 | 已确认事实、假设、待办、已尝试方案及结果 | 作为可更新投影；重要事实附来源 |
| 节点工作状态 | 本节点输入、局部历史、待执行操作 | 默认只向所属节点提供必要部分 |
| 原始证据与产物 | 文件版本、工具原始结果、补丁、测试报告 | 不可变保存或引用固定版本，可按需回查 |
| 摘要与检索结果 | 对历史和证据的压缩、筛选 | 属于派生内容，记录覆盖范围和来源；不替代原文 |

共享状态不等于所有节点共享全部聊天历史。节点上下文隔离是数据可见性约束，不自动提供进程或操作系统权限隔离。

### 4.2 每次模型调用的组装流程

1. 读取当前目标版本、有效约束、节点契约和权限。
2. 加入节点所需状态、最近有效结果及与当前待办相关的证据。
3. 根据上下文额度裁剪可选历史；核心约束放不下时显式处理，不能静默删除。
4. 对需要压缩的历史生成摘要，保留来源范围、摘要版本和原文入口。摘要中的推测不能自动升级为事实。
5. 记录实际发送的消息、工具定义、模型参数及对应证据引用，形成可重建的模型请求。
6. 将模型响应记录后交给节点逻辑；如果发现证据不足或摘要冲突，允许重新读取原始内容。

大工具结果先保留原始内容，再产生有界的模型可见视图。仅保存截断后的文本，会失去回查能力。模型看到的内容及其变换过程应能由应用侧记录重建；该要求不包含不可见的模型内部状态。

外部资料和工具响应作为证据处理，不能直接覆盖可信目标、扩大工具权限或改变验收标准。用户更正通过明确的输入事件更新目标版本，并使相关节点重新组装上下文。

文件路径和 URL 只能定位资源，不能证明内容未变。使用影响决策的证据时，应保存内容快照或可取回的不可变版本，并记录内容哈希。恢复执行前检查当前工作区与预期版本是否冲突；冲突作为新观察记录并处理。

### 4.3 最小验收

- 关键目标和约束在多次上下文重组后仍出现在相关请求中。
- 摘要中的重要结论能定位到原始证据；查不到时标记缺证据。
- 对“压缩后遗漏约束”“摘要错误”“证据已变化”各有专门案例。
- 统计重复读取、重复尝试、约束违反和上下文成本；保存历史的大小不能作为记忆效果指标。

## 5. 事件、checkpoint 与工具恢复

### 5.1 权威数据与提交边界

SQLite 保存权威事件、调用记录、run 元数据和 checkpoint。当前状态是事件经 reducer 得到的投影，可以缓存或存表，但不能绕过事件独立修改。JSONL 是导出格式，不与 SQLite 并列成为两个需要实时双写的事实来源。

大产物可存入不可变内容存储，由数据库事件引用。必须先完成产物的持久化，再提交引用它的事件；崩溃产生的孤立产物可以后续清理，已提交事件不能指向尚未可靠保存的内容。

模型响应、工具结果、人工输入、时间触发和随机结果以已记录观察进入确定性状态更新。事件按每个 run 的递增序号排序；时间戳辅助审查，不承担唯一排序职责。

建议的最小记录字段如下，具体表结构在 Phase 1 固定：

| 记录 | 必要信息 |
| --- | --- |
| Run 元数据 | run_id、parent_run_id、目标和配置版本、有效 Graph 快照、开始时间、验收及预算策略 |
| 事件头 | event_id、run_id、run_seq、event_type、event_schema_version、kernel_version、recorded_at、因果关联 ID |
| 节点执行 | node_id、node_execution_id、输入状态版本、局部执行进度、结果与验证证据 |
| 调用 | operation_id、attempt_id、模型／工具身份与版本、请求、结果、重试分类、费用状态 |
| Checkpoint | run_id、last_event_seq、state_schema_version、对应状态及未决调用投影 |

已解析的 Graph、提示词、工具定义和模型参数可以存成有版本的公共记录，由事件引用，避免每个事件头重复大内容。配置哈希应针对展开默认值后的有效配置，不能只对原始 YAML 文本计算后就认为配置一致。

审计的决策依据包括输入、可见模型输出、采用规则和验证结果；不假定能够获取模型未返回的内部推理。

### 5.2 最小可恢复执行单元

Graph 节点可以是确定性函数、工具调用、模型调用或局部 Agent Loop。Agent Loop 即使在配置上表现为单节点，也必须暴露模型调用、工具派发、结果接收和等待点的局部进度，不能等整段 Loop 完成才落盘。

一次执行的基本顺序为：

1. 根据已提交状态确定下一步，校验输入、权限和额度。
2. 持久化操作意图、稳定的 operation_id、请求内容及预算预留。
3. 在开始外部调用前，持久化进入派发阶段的标记，再由适配器执行 IO。
4. 收到结果后记录原始响应及执行状态；结果是否通过业务校验另行记录。
5. 在数据库事务中提交相应事件、状态投影、预算变化和可持久化的后续调度意图，然后继续执行。

数据库事务可以协调内部记录，不能包含并原子提交任意远端 API 或 shell 副作用。工具执行成功但业务输出不合格时，仍需保留执行成功的事实，不能因 schema 校验失败而自动重做写操作。

### 5.3 恢复语义按工具分类

恢复时先重建已提交状态，再检查未决调用、工作区版本和执行者身份，完成核对后才派发新动作。

| 类型 | 已派发但未记录结果时的策略 | 约束 |
| --- | --- | --- |
| 只读 | 允许按策略重新读取 | 外部数据可能变化；新读取作为新观察，不能冒充旧结果 |
| 有幂等保证的写操作 | 使用原 operation_id 或幂等键重试 | 明确服务端支持范围、去重有效期及请求内容一致性 |
| 可查询完成状态的写操作 | 先查询，再决定复用结果、等待或重试 | 查询必须能可靠关联到原逻辑操作 |
| 无法确认结果且不可安全重试 | 标记 Unknown，进入 Waiting／ToolOutcomeUnknown | 由人工或专门核对器决定下一步；不得盲目重放 |

一次业务操作的多次重试共享 operation_id，attempt_id 随尝试变化；新的业务迭代使用新的 operation_id。去重必须在接收操作的一侧实际有效，仅给请求附一个 ID 不会自动带来幂等。

对本地补丁写入，可结合预期原文件哈希、目标内容哈希和原子替换实现可核对行为；追加写入和通用 shell 不能默认视为幂等。远端超时、连接断开、进程退出和取消都不能单独证明操作未生效。

本项目不承诺任意外部工具的 exactly-once 执行。承诺是在已声明的工具恢复策略范围内处理结果；不能确认时保留未知状态，而不是虚构成功或安全失败。

### 5.4 用户等待与恢复输入

等待记录至少包含 wait_id、run_id、等待原因、预期输入 schema、关联操作、目标／状态版本和可选截止时间。进入等待时停止派发相关操作，并持久化恢复所需内容，释放不再需要的执行资源；等待不等于删除持久化数据。

恢复输入携带稳定 input_id 和 wait_id，在同一事务中完成去重、记录输入及消费等待。重复输入返回已有处理结果；过期、目标不匹配或已被处理的输入不得触发第二次执行。人工审批应绑定具体操作内容，内容变化后旧审批不再适用。

首轮实现一次性用户输入／确认即可。运行中持续纠偏、多个等待者、信号队列和复杂节点间协调后续按需扩展，不一次性复制全部 durable execution 原语。

### 5.5 三种历史操作

| 操作 | 行为 | 保证边界 |
| --- | --- | --- |
| 审计重建 | 加载记录和产物，折叠事件重建历史状态 | 不调用真实模型或工具；在已支持版本内要求状态语义一致 |
| 断点续跑 | 重建状态、核对未决调用、继续真实执行 | 起点可解释；后续模型输出和外部数据可能不同 |
| 分叉执行 | 从指定历史点建立关联 run，应用新输入并执行 | 记录分叉来源；不自动回滚文件、数据库或远端系统 |

日常审计通常要求关键字段和业务语义一致，不要求所有序列化字节逐比特相同。若某类记录用于内容寻址或签名，应对该类记录另行定义规范化编码和字节一致性。

Checkpoint 是某事件序号对应的状态快照和加速入口。恢复加载快照后重放后续事件；没有快照时可从保留的完整事件前缀重建。创建快照本身不授权删除历史；历史保留和产物清理必须遵守已承诺的审计及分叉范围。

配置哈希、模型 ID 和采样参数只能识别部分环境。保存原始请求与响应才能解释历史行为；再次使用同名模型不保证得到原响应。工具版本、环境摘要、文件基线和相关证据也应记录，但不宣称可重现全部外部世界。

### 5.6 兼容性、持久性与故障范围

事件 schema、状态 schema、Graph 配置和 kernel 分别版本化。运行中不静默热替换 Graph、reducer 或工具定义；升级时使用已测试的兼容读取／迁移策略，不支持的旧记录明确拒绝继续执行，保留原始数据供旧版本审计。

迁移在副本上验证，保留原事件或可还原备份。Rust 编译成功不能替代旧事件和旧 checkpoint 恢复测试。对支持的版本集合维护黄金事件流，验证完整重放与“快照＋后续事件”得到相同语义状态。

首轮可靠性范围是同机进程崩溃、重启、普通请求失败和重复恢复输入。SQLite 的事务、同步设置及产物落盘策略需要明确并测试；断电和磁盘损坏的保护需要额外验证或备份，不能由一次 kill 测试推导。磁盘满或记录写入失败时停止新派发，优先保全已有状态。

## 6. 预算、工具权限与运行边界

### 6.1 预算账本

预算覆盖主任务、局部 Loop、规划与验收模型、上下文摘要、重试和未来的子 Agent。分别记录输入／输出 token、调用次数、活跃时间、外部等待时间和货币成本估算；异构模型的 token 数不能直接等同于货币成本。

调用前校验并预留额度，调用后按服务返回的 usage 结算。未返回 usage 的请求保留“估算／未知”标记；无法确认费用时不能直接把预留全部释放后继续无限重试。适配器应定义估算规则和可用的输出上限，严格成本边界还取决于服务商实际计费与限额能力。

恢复继续原账本。若用户追加预算，记录变更事件；新 run 继承任务继续执行时应明确沿用还是新增额度，并保留累计展示。达到预算后停止新派发，处理在途操作，不能只在节点结束时检查一次。

上下文窗口、单次输出、工具结果字节数、请求超时、总运行时间和最大逻辑步数分别设限。外部等待通常不计活跃执行时间，但可以具有独立截止时间。

### 6.2 工具执行管线

统一管线为：输入与权限校验 → 必要的用户确认 → 持久化调用意图与额度 → 执行／超时／取消 → 记录原始结果 → 生成模型可见视图 → 业务校验及状态提交。

失败重试由工具恢复分类控制，不是所有异常都套同一种重试包装。自动升级权限也不是默认恢复策略。

有限工具至少声明：名称与版本、输入／输出契约、资源范围、读写性质、重试与核对策略、超时、输出上限，以及必要时的用户确认方式。子 Agent 的工具权限不能因派生而自动扩大。

最初的固定验证命令优先使用可执行文件和参数数组，避免任意字符串 shell 拼接。工作目录限制不能单独阻止子进程访问其他资源；需要执行不可信代码时应使用适当隔离环境。若没有这样的环境，保持工具子集受限并在验收中说明能力边界。

### 6.3 记录与生命周期

模型可见内容在获准记录的范围内可重建；认证头、API 密钥等不应进入模型上下文或普通日志。工具输出在进入模型前按策略过滤，记录变换过程。若用户要求删去敏感历史，应明确其对应审计能力随之受限，不能同时承诺删除与完整重建。

工具连接和本地资源采用明确的创建、使用、关闭流程。RAII／Drop 用于本地资源清理；异步关闭、取消收尾和外部业务补偿应显式设计。强制终止时不能保证 Drop 执行，补偿动作本身也可能失败，不能将资源清理等同于事务回滚。

## 7. 技术选型与架构

### 7.1 语言决策：Rust

保留 Rust，主要依据是维护者个人偏好、长期学习目标、控制信息的类型建模和原生二进制部署需求。Rust 能帮助阻止一类内存、所有权与并发误用；它不能自动证明业务正确、外部 IO 幂等或旧数据迁移正确。

Go、TypeScript 和 Python 都能实现可靠运行时。TypeScript 有静态类型，但运行时外部输入需要校验；Rust 和 Go 读取不可信或跨版本数据同样需要边界校验。语言选择不应被表述为“长程任务必然排除某种语言”。

| 语言 | 与本项目相关的收益 | 需要承担的成本 | 决策 |
| --- | --- | --- | --- |
| Rust | 类型化控制状态、所有权约束、原生部署 | 异步取消语义、编译反馈、部分 SDK 适配 | 当前主线 |
| Go | 熟悉度、较直接的服务端开发和部署 | 动态载荷仍需校验，取消依赖各层配合 | 若 Rust 成本阻碍核心验证，可重新评估 |
| TypeScript | Agent 生态、动态组合与 API 集成便利 | 运行时数据校验、依赖管理、取消传播纪律 | 合理替代，不因语言类别排除 |
| Python | 快速实验、Agent 与评估生态 | 打包、运行时约束和异步／进程管理 | 适合实验和外围，也可实现内核 |
| C++ | 既有经验、原生部署与底层能力 | API、异步、序列化和协议集成的额外工作 | 当前负载没有足够理由承担这些成本 |

取消是各层需要配合的协议。Go context、TS AbortController 和 Rust 异步任务取消都不能单独保证远端副作用终止；选择语言不能替代 §5 的恢复语义。

### 7.2 Rust 类型边界与依赖

控制信息使用结构体、枚举和明确 ID 类型，例如 RunStatus、Event、NodeExecution、Operation、BudgetLedger。开放的业务载荷允许使用 `serde_json::Value`，在节点契约边界做 JSON Schema 与业务校验；已稳定的业务类型可逐步类型化。不要求整个 Graph 泛型化，也不把整个运行时降为无结构 JSON。

节点执行器可采用统一接口和运行时注册；是否使用 trait object、如何表达异步返回值按实际需求确定。避免为了未来插件能力提前设计复杂的宏系统或类型体操，也不笼统禁止 serde 等常用派生宏。

| 能力 | 候选依赖或实现方式 | 采用前检查 |
| --- | --- | --- |
| 异步运行 | tokio | 超时、取消安全性、子进程回收方式 |
| HTTP | reqwest 或满足接口的 SDK | 目标服务支持、代理／证书、流式处理、重试语义 |
| JSON | serde／serde_json | 事件版本、数值表示、必要的规范化规则 |
| SQLite | rusqlite，按目标平台评估 bundled | 事务、同步模式、备份、阻塞操作与异步调度边界 |
| Schema 校验 | jsonschema 等候选 | 选用的 JSON Schema 草案及错误可解释性 |
| 配置 | 首轮 JSON；需要 YAML 时选择仍维护的解析器 | 重复键、隐式类型、配置版本及未知字段处理 |
| CLI 与错误 | clap、thiserror；边缘层按需 anyhow | 用户可处理错误与内部缺陷区分 |
| MCP | 官方项目或活跃社区 SDK 候选 | 固定协议版本、目标 transport 和 tools 子集的实际互通 |

该清单是实现候选，版本与维护状态在采用前核查并锁定。不以未经核实的 MCP SDK Tier 或协议发布日期决定语言；不承诺“兼容 API 就覆盖全部服务”。首轮选择一个服务、一个模型、一个端点及明确的工具调用子集，错误、流式中断和 usage 缺失也要验证。

### 7.3 模块职责与依赖方向

```text
CLI / 未来 UI
    → 应用服务：创建、运行、等待、恢复、审计、导出
        → 运行时：调度、状态机、契约、预算、确定性 reducer
            → 定义存储、模型、工具、验收器等接口
        → 接口实现：SQLite、HTTP 模型适配、文件工具、进程工具、未来 MCP

上下文组装器和可选规划 Agent 通过已定义接口参与执行。
协议与事件类型供各模块共享；运行时不依赖具体前端或模型厂商。
```

先以少量模块落实依赖边界，确认存在独立编译或复用需要后再拆 crate。可复用的内核库与独立协议类型值得保留，但不复制大型项目的全部模块数量。

### 7.4 架构方案比较

| 方案 | 决策 | 原因与重新评估条件 |
| --- | --- | --- |
| 单体内核＋进程外工具 | 当前主线 | 部署与调试范围可控；需自行管理工具权限与生命周期 |
| 事件记录驱动状态投影 | 从 Phase 1 建立 | 符合审计和恢复需求；增加 schema、提交顺序和迁移工作 |
| Temporal／Restate 等持久执行引擎 | 当前不引入 | 主要顾虑是依赖、部署和维护成本；未来生产可靠性需求扩大时重评 |
| 分布式 worker | 当前不做 | 暂无实际多机需求；避免先引入部分失败和协调复杂度 |

事件溯源并非审计的唯一实现方式，快照配合完整操作记录也能满足部分需求。本项目选择事件记录驱动状态，是为了统一历史解释与状态恢复；回放、保留策略和版本演进不会免费获得。

持久执行引擎的确定性约束可通过把 LLM／工具 IO 放入 activity 等边界来满足，不能据此断言它们不支持灵活路由。是否采用取决于整体成本和需求，而不是是否所有代码都由自己编写。

## 8. Graph 配置与节点契约

### 8.1 最小声明能力

先用程序构造一个能够循环修正的图，验证运行时语义，再开放数据配置。首版 DSL 仅支持：

- 配置版本、入口节点、节点及边列表。
- 节点执行器引用、input/output schema 引用、输入状态视图和允许更新字段。
- 可选模型配置引用、已注册工具集合、固定上下文策略及局部限额。
- 指向已注册确定性谓词的条件边，以及明确的成功／停止等出口。
- Graph 级预算、验收器和等待／重试策略。

首版不在 YAML 中嵌入任意脚本，不支持运行时生成任意节点类型。配置里的模型、工具、谓词和校验器引用必须能解析到已经安装且获准使用的能力。“不改代码换流程”的含义是重组已有能力，不等于任意新业务都能通过配置完成。

### 8.2 执行前与运行时校验

执行前检查节点 ID 唯一、引用存在、入口有效、节点可达、配置版本支持、契约可用及资源限额完整。有环是合法结构；静态检查只能验证出口和上限声明，不能证明所有数据路径都能成功终止。

首版条件边不提供隐式优先级。一次决策必须命中唯一后继，或命中显式默认分支；多分支同时命中、缺少后继、模型指定不存在的边都作为可解释错误处理。将来需要优先级时，作为有版本的显式语义增加。

运行时再检查实际输入输出、字段写入范围和当前权限。类型 schema 通过后仍可能需要业务校验；工具已执行而输出无效的情况遵守 §5 的副作用规则。

### 8.3 默认 Loop、模型绑定与配置演进

默认 Agent Loop 复用相同的事件、调用、预算和等待机制，在控制图中可以表现为单个复合节点，其内部仍按 §5.2 记录恢复进度。禁止形成一套 Graph 持久化和另一套不可恢复 Loop 的双轨实现。

节点契约可以早期预留 `model_ref`，先全部指向同一配置。异构模型的实际组合与收益在 Phase 4 验证；不需要先实现主 Agent、并行或进程隔离才能配置不同模型。

首轮采用一个有效配置来源和明确默认值，提供导出有效配置的调试入口。多层 patch、热替换和复杂插件继承规则等出现需求后再加，避免配置数量膨胀。在途 run 始终绑定创建时的有效配置版本。

## 9. 分阶段路线图与工期边界

### 9.1 排序原则

先定义实际任务和验收，再验证执行可靠性，然后接入真实模型和上下文；Graph 配置、复杂进展策略和多 Agent 逐步增加。错误恢复、预算及权限属于执行骨架，不能等生态阶段才补。

每个阶段都有独立产物和进入下一阶段的条件。发现核心假设不成立时，可以缩小范围、调整实现或采用已有框架，不为进入下一阶段而积累没有效果的功能。

## 10. 验收方法与实验设计

### 10.1 两条验证线

运行时正确性与模型任务效果分别验证。前者使用模拟模型、工具和可控故障，以确定性断言为主；后者运行真实模型，保留重复实验、成本和失败记录。真实模型一次成功不能替代故障测试，模拟任务的全部通过也不能证明模型质量。

首轮约 20 个固定案例，每例建议重复 3 次，作为早期发现问题与比较趋势的起点。案例不够时报告实际数量；不能将同一案例的多次运行当成同数量的独立任务，也不把小样本结果包装成生产可靠性证明。

比较普通 Loop 与 Graph 时，尽量保持模型、工具能力、任务资料、验收和预算一致。节点提示可以按职责组织，但不向某一方案额外提供答案或关键资料。异构模型、上下文策略和主 Agent 的作用采用逐项加入／移除的对照，避免无法解释收益来源。

### 10.2 必测故障与边界场景

| 场景 | 预期行为 |
| --- | --- |
| 操作意图已落盘，尚未进入派发阶段时崩溃 | 恢复后可按记录继续派发，逻辑操作身份保持一致 |
| 已进入派发阶段，但是否抵达外部服务未知 | 按工具分类查询、幂等重试或挂起，不能直接假设未执行 |
| 写操作成功，结果尚未落盘时崩溃 | 模拟幂等工具不产生重复效果；不可安全重试工具进入 Unknown |
| 结果已落盘，节点状态或后续调度尚未完成时崩溃 | 使用已有结果继续，不重复执行已确认操作 |
| 同一结果或恢复输入重复到达 | 去重后返回已处理结果，不重复更新预算或派发 |
| 两个进程同时恢复同一 run | 仅一个取得执行权，另一个得到明确提示 |
| 预算临界点、恢复后继续、usage 缺失 | 不重置额度，不把未知费用当零，不越过已定义的派发限制 |
| 超时或取消后工具仍在执行 | 停止新派发，登记在途／未知状态并核对，不假装副作用已撤销 |
| schema 不合格、非法边、没有合法后继 | 拒绝非法迁移并保留诊断；已发生的工具效果仍可追溯 |
| 合法修正循环与无效重复调用 | 正常循环不只因节点重复被误停；记录任务进展证据 |
| 上下文摘要丢约束、证据版本变化 | 能检测或通过用例暴露遗漏；可回查原文并记录新观察 |
| 等待输入过期、审批内容变化 | 拒绝错误关联，不复用已失效确认 |
| 数据库写入失败或磁盘满 | 停止新派发并报告存储问题；不得继续制造未记录副作用 |
| 旧版本事件／checkpoint | 支持版本得到相同语义状态；未知版本保留数据并明确失败 |
| 审计重建与历史分叉 | 审计无真实 IO；分叉记录来源，不声称自动撤销外部世界 |

故障测试必须能控制中断位置并核对外部模拟效果，不能只验证“程序能重启”。对实际支持的文件工具、模型服务和子进程再做有针对性的集成验证。

### 10.3 效果指标

| 维度 | 记录内容 |
| --- | --- |
| 完成质量 | accepted／rejected／inconclusive 比例、基线测试与回归结果、人工复核意见 |
| 信息连续性 | 约束违反、关键事实遗漏、重复尝试、原始证据回查情况 |
| 恢复行为 | 中断后的恢复结果、重复效果、未知调用是否被识别、人工核对成本 |
| 停止策略 | 正常任务误停、无效循环漏检、触发依据和后续可恢复性 |
| 成本与性能 | token、费用估算、调用数、活跃／等待时间、恢复耗时、事件存储增长 |
| 使用负担 | 配置修改量、人工介入次数、理解失败原因和完成恢复所需操作 |

在 Phase 0 预先记录可接受的质量与成本取舍，避免看完结果后改变成功标准。若 Graph 没有改善目标指标，应检查任务选择、上下文和验收机制，允许保留更简单的 Loop。有限功能内的正确性是必须项，模型质量提升属于需实验检验的假设。

### 13.2 Phase 0 必须固定的内容

以下属于实施准备，并非要求先扩充内核功能：

1. 实际试点仓库或其他任务来源、案例列表、难度范围及验收资料。
2. 首个模型服务与端点、可用工具、单任务预算和实验总预算。
3. 实验工作区与隔离方式、允许的写入范围、需要确认的操作。
4. 约束保持、质量和成本的可接受取舍，以及基线运行方式。
5. 目标平台、每周可投入时间和 Rust 熟练度，据此修订工期区间。

每次新的技术决策记录问题、候选方案、采用理由、已知代价、验证方法和重新评估条件，并同步修改正文对应章节，避免继续通过追加互相矛盾的“最终结论”维护设计。
