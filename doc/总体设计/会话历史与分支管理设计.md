# 会话历史与分支管理设计

> 状态：设计讨论；以下为建议语义，尚未实现。
>
> 核心问题：一次会话可经过多个工作流 Node；一个 Agent Loop Node 内又可发生多次模型请求和工具调用。会话树中的一个点应对应哪一层？

从旧分叉点实际重做时的工作区、数据库和外部副作用处理，另见[分支重做与外部状态管理（待定设计）](分支重做与外部状态管理-待定设计.md)。

## 1. 建议结论

**实现层的检查点可以细化到每次已完成的模型调用或工具调用；使用层的默认分叉应落在语义稳定的决策边界。** Runtime 为每次调用前后可恢复的状态建立检查点，完整过程另以事件记录。调用开始、响应尚未到达或工具仍在执行时不能直接分叉；已完成的调用也必须满足待处理操作和外部状态可重建的条件。只有当检查点代表了一个可理解、可比较、值得尝试另一条路径的任务状态时，才默认作为用户可见的分叉点。

这里有三种不同的“节点”，需要分开称呼：

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 工作流 Node | 用户配置的执行单元，类型为 Agent Loop Node 或 Control Node | “修改代码”“运行编译和测试” |
| 历史事件 | 已发生的一项操作或结果，按发生顺序记录 | 模型请求、模型响应、工具调用、工具结果、路由决定 |
| 调用检查点 | 调用完成后记录的机器可恢复状态 | 一次模型响应已记录、一次工具结果已提交 |
| 语义检查点 | 产物、判断或路由已经形成，用户能理解从这里尝试另一方案的状态 | Agent Loop Node 提交候选修改，Control Node 给出测试失败结果 |
| 会话分叉点 | 对用户开放的语义检查点；从这里创建新分支有明确目的 | “基于当前修改再试一种实现”“从测试失败处走另一条修复路径” |

工作流 Node 可以执行多次，每次执行有独立身份；一次执行可产生多个历史事件和检查点。因此，不能用工作流 Node 的名称或一次调用代表整段会话历史。

## 2. 粒度选择

| 方案 | 优点 | 问题 |
| --- | --- | --- |
| 每次工作流 Node 执行是一个会话树节点 | 树较小，容易展示 | 长 Agent Loop 内部变成黑盒，无法从中途分叉或精确恢复；模型和工具明细仍需另存 |
| 每条模型或工具事件都直接成为可分叉的树节点 | 可以定位任意记录 | 请求可能尚无响应，工具可能仍在执行；模型一次响应可触发多个工具，任意事件位置不一定有可继续的状态 |
| **每次已完成调用后建立检查点，语义边界才作为默认分叉点** | 既能细粒度恢复，也不会把大量没有独立意义的中间状态暴露为分支 | 需要节点报告产物、状态和决策边界，并区分“可恢复”与“适合分叉” |

推荐第三种。这里的“树”描述历史分叉关系，不要求把每条事件都物理存成树节点。调用检查点可以轻量地引用事件和状态增量；语义检查点在此基础上声明可展示的分叉理由和继续条件，不要求每次复制完整对话或工作区。具体存储格式以后确定。

## 3. 一个 Agent Loop Node 内如何记录

模型请求及响应是一项模型调用，工具派发及结果是一项工具调用。每项调用各自保留开始和结束事件；完成时建立检查点。若模型一次响应要求多个工具，模型调用后的检查点保存这批待处理工具；串行执行时，每完成一个工具都更新剩余队列并建立检查点。模型下一次请求仍需遵守协议，不能因为分叉就丢弃未处理的工具调用。

```text
检查点 P0：进入“修改代码” Agent Loop Node
  事件：模型请求 #1 → 模型响应 #1，请求工具 A、B
检查点 P1：模型调用 #1 完成；待处理 A、B
  事件：工具 A 调用 → 结果
检查点 P2：工具 A 完成；待处理 B
  事件：工具 B 调用 → 结果
检查点 P3：工具 B 完成；本批工具已结清
  事件：模型请求 #2 → 模型响应 #2，给出最终产物
检查点 P4：模型调用 #2 完成
  事件：Agent Loop Node 完成
检查点 P5：离开“修改代码”节点
  事件：Control Node 执行编译与测试、记录结果并路由
检查点 P6：Control Node 完成
```

`P1`、`P2` 和 `P3` 是调用检查点，但不必默认显示为用户分支。若模型响应只是请求更多工具，或工具结果只是补充上下文，这些点通常没有独立的使用意义。模型形成候选修改、Agent Loop Node 提交阶段性产物、Control Node 产生测试结论时，Runtime 可将对应状态标记为语义检查点。界面可以默认折叠成工作流 Node 执行摘要，再展开模型与工具明细；展示层级不改变底层记录粒度。

## 4. 何时允许分叉

默认允许分叉的位置是**已提交、可继续且具有语义目的**的检查点：进入或完成工作流 Node、Agent Loop Node 提交阶段性产物、Control Node 产生检查结果和路由决定，或用户明确从某个调用检查点发起“另试一种路径”。调用仍在进行时不能分叉。模型响应产生待处理工具时，分支必须继承其调用身份与待处理队列；从工具 A 结果后分叉，工具 B 仍待处理。如果要放弃或改写这些待处理调用，必须有显式的取消或重新规划操作，而不能静默丢弃协议状态。

单次模型或工具调用只有在它本身形成了独立的任务选择时，才适合作为用户分叉点。例如模型已经提出两个可比较的实现方案，或一次只读检索已经形成不同的证据路径。仅仅因为调用完成，并不代表用户有理由创建新分支。

串行调用可以在每次完成后评估是否允许分叉。若一批工具并行运行，在其他调用仍在途时不开放分叉；至少等整批结清，或先实现可靠的取消、隔离与状态核对。某次调用虽已返回，但外部副作用无法为新分支重建时，其检查点仍可用于查看历史，暂不标记为可分叉。

从旧检查点分叉时，新分支引用该检查点及其祖先历史，后续事件只追加到新分支；原分支不被覆盖。沿原分支继续与从旧位置重新尝试是两种操作：后者会产生新分支和新的模型／工具调用身份。兄弟分支只在明确引用产物时交换信息，不自动合并上下文。

检查点必须能定位继续执行所需的状态：当前工作流位置、所在 Node 的局部进度、有效配置与插件版本、剩余预算、上下文资料引用，以及适用时的工作区状态。检查点可以引用已记录事件重建这些状态，不要求每次复制完整历史。历史费用与已发生的副作用不会因分叉而消失；分支预算如何分配需由会话级策略明确规定。

会话树不会自动复制文件系统。若分支涉及写文件、运行测试或其他外部操作，恢复分支前必须关联并核对相应的工作区快照或独立工作区。工具结果未知时先完成核对；不能因为事件里缺少结果就重新执行有副作用的调用。

## 5. 节点插件与 Runtime 的分工

Runtime 统一分配会话、分支、工作流 Node 执行、模型调用、工具调用、事件和检查点的身份，并负责持久化、分叉、恢复和上下文读取。用户自定义的 Agent Loop Node 应向 Runtime 报告每次模型请求／响应、工具调用／结果及剩余待处理操作；自定义 Control Node 应报告检查操作、结果和路由决定。插件不能私下维护一份与会话树脱节的权威历史。

若某个插件的内部操作无法报告，Runtime 只能把该节点作为不透明执行单元记录，最细分叉点退化到节点完成处；这应作为明确的能力限制，而不是假装可以在其内部恢复或分叉。是否允许这种插件，以及最低事件报告契约，需要在插件接口设计时确定。

## 6. 仍需确认的设计点

1. 如何让 Agent Loop Node 声明语义检查点：由插件主动报告，还是由 Runtime 根据结构化产物和状态自动识别。
2. 分支创建后如何分配模型、时间和工具预算：共享会话总额、在分支上另设上限，还是两者兼有。
3. 会话记录中模型请求、工具输出及大文件产物的保存范围与引用方式；哪些内容需要摘要，哪些必须保留原始证据。
4. 分支工作区采用独立目录、版本控制工作树还是快照；如何判定外部副作用在分叉时可重现。
5. 初版是否支持同时运行多个分支。树型历史不依赖并行执行；并行时还需解决工作区隔离和预算并发更新。

## 7. 与当前实现的关系

Step 0 将模型交互历史放在内存中的线性列表，未保存完整会话记录，也没有会话树、检查点或分支恢复。本设计是后续 Runtime 的目标语义，不把现有 Loop 描述为已经支持这些能力。首个验证案例应在一个 Agent Loop Node 内完成至少两次模型调用和多个串行工具调用：底层验证每次调用都能恢复，上层只从阶段性产物或 Control Node 检查结论创建用户分支，并检查待处理调用、上下文与工作区状态互不混淆。
