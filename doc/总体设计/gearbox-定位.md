# gearbox：整体定位

> 状态：方向草案。描述目标与设计边界，不代表功能已经实现。

## 1. 项目定位

`gearbox` 面向长程任务，是一个可扩展的基础 Agent Runtime。它提供可独立使用的 Agent Loop，并由 Runtime 管理工作流执行和树型、多分支的会话历史。Pi Agent 一类轻量 Agent Runtime 是基础能力的参照；`gearbox` 希望在此基础上提供更灵活的工作流编排与统一插件扩展。

长程任务需要在多次模型调用和工具操作中保持任务目标与证据可用，在确定的检查点执行验证，并在失败、中断或预算耗尽后知道已完成什么、如何继续。模型给出最终回答并不等于任务已通过验收。

## 2. 做什么

- **提供基础 Agent Loop**：调用模型、执行工具，并把结果交回模型继续处理任务；这个能力也可以独立使用。
- **编排工作流**：启动节点、传递任务输入与产物、依据规则选择合法的后继，记录进度和停止原因。默认工作流只有一个 Agent Loop Node；用户需要明确验证或分工时再增加节点。具体节点类型、路由与示例见[工作流设计](工作流设计.md)。
- **管理会话历史**：由 Runtime 记录模型、工具和工作流执行，允许从可继续的历史点创建分支、切换分支并继续。检查点粒度、分叉条件与工作区状态要求见[会话历史与分支管理设计](会话历史与分支管理设计.md)。
- **统一扩展能力**：通过同一套插件发现、加载、配置和生命周期机制注册用户自定义的 Agent Loop Node、Control Node 和工具；模型接入、上下文策略和 skill 等也应能沿用这一机制扩展。内置能力和用户实现遵循相同的节点契约。
- **支撑长任务运行**：保存任务目标、约束、关键产物与检查证据；管理预算、取消、停止和恢复。中断后核对可能已经发生的外部副作用，再决定重试或继续。

## 3. 不做什么

- 不把编译、测试、Review 等场景固化为框架预设的节点种类；具体步骤和节点实现主要由用户定义。
- 不把模型的完成声明当作验收结果。需要验证的任务由工作流执行实际检查；开放式任务可以交由人工判断。
- 不把会话分支当作文件系统隔离或自动合并。涉及文件修改的分支需要可恢复的工作区状态或独立工作区，跨分支复用产物必须明确引用来源。
- 现阶段不预设通用 Graph DSL、多 Agent 并行、插件热加载或模型辅助路由。这些能力是否需要、如何设计，由具体任务验证后决定。

## 4. 当前设计决策与实施边界

目前确定的两项设计方向分别记录在[工作流设计](工作流设计.md)和[会话历史与分支管理设计](会话历史与分支管理设计.md)。前者规定节点如何执行、循环和结束；后者记录实际发生的执行，以及历史从哪里分叉、各分支如何演进。同一个工作流节点可以在不同分支上运行多次，不能只靠节点名称定位历史。

当前 [Step 0：最小 Agent Loop](../阶段方案/step-0-最小Agent-Loop实现方案.md) 仅验证模型与只读工具的往返，历史仍是内存中的线性列表。工作流编排、树型会话、插件、持久化和恢复尚未实现；具备相应能力并经过验证前，不宣称长程任务已可靠执行。
