# 分支重做与外部状态管理（待定设计）

> 状态：待定。记录会话历史分叉后的执行状态问题、候选策略与未决事项；不代表 Runtime 已具备回滚、快照或重做能力。
>
> 关联：[会话历史与分支管理设计](会话历史与分支管理设计.md)讨论分叉点的记录粒度；本文讨论从过去的分叉点**实际执行**另一方案时，如何处理已经改变的环境。

## 1. 问题与术语

一次任务可能同时改变会话历史、工作区、数据库和远程服务。从旧历史点建立新分支，只复制了逻辑上的任务上下文；原方案已经产生的外部效果仍然存在。要从该点真正重做，必须知道新分支将在哪个环境状态上运行。

| 操作 | 含义 | 是否改变已有分支或外部世界 |
| --- | --- | --- |
| 历史分叉 | 共享分叉点之前的记录，为新方案追加独立历史 | 不撤销既有操作 |
| 环境复制 | 为新分支构造与分叉点相符的独立文件、数据库或其他资源状态 | 可以保留原方案继续运行，但依赖资源可复制 |
| 回滚 | 把某个受控资源恢复到旧状态 | 会改变该资源当前状态；不等于撤销所有外部效果 |
| 重做 | 从选定状态发起新的模型与工具操作，形成新尝试 | 产生新的调用身份、费用和可能的新副作用 |

**候选原则：优先在独立环境中重做，保留原分支及其状态。** 不因为新建会话分支就自动回滚原方案使用的共享工作区。若只能使用同一环境，必须先保存和核对现状，再确认恢复范围与后果；是否允许这种模式待定。

重做也不保证产生与过去相同的结果。模型输出、网络服务和外部数据可能变化。使用旧事件重建历史用于审计；再次实际调用模型或工具是一次新的执行，不应伪装成原调用的继续。

## 2. 一个分叉点需要哪些状态

分叉点不能只保存消息位置。至少要能关联以下状态或明确标注无法恢复的部分：

- **会话与工作流**：当前分支、Node 执行位置、待处理模型／工具调用、配置和插件版本、预算消耗及上下文引用。
- **本地工作区**：已跟踪与未跟踪文件、文件元数据、配置、所依赖的构建或运行环境；只保存 Git commit 不一定足够。
- **受控数据**：数据库、对象存储、缓存或容器状态，以及可用的事务、快照和隔离范围。
- **外部效果**：远程 API、部署、邮件、支付、用户或其他系统的操作及其回执；其中一部分无法还原。
- **外部观察**：检索结果、时间相关数据和其他只读观察。旧结果可以作为当时的证据，但重做时外部世界可能已经变化。

检查点可引用独立的状态清单或快照，不要求把这些内容全部复制进会话事件。若状态范围未知，就不能据此宣称分支可从过去精确重做。

## 3. 不同场景的候选策略

| 场景 | 可考虑的做法 | 主要边界 |
| --- | --- | --- |
| Git 管理的代码 | 记录基线提交和工作区改动，为新分支创建独立 worktree 或目录 | Git 不覆盖未捕获的未跟踪文件、数据库、进程和远程操作；共享构建产物也可能互相影响 |
| 普通文本或文件集合 | 内容版本、目录快照或复制到独立工作区 | 还需保留路径、元数据、附件及外部引用；大文件复制成本待评估 |
| 数据库任务 | 事务回滚、测试库、数据库快照或临时实例 | 事务提交后的外部消费者、跨库写入及消息队列不一定能同步回滚 |
| 容器或可重建服务 | 从镜像与配置新建隔离实例，必要时恢复数据卷 | 镜像、依赖、密钥与外部连接必须匹配；容器快照不覆盖外部服务 |
| 只读外部查询 | 保存旧响应作为证据；重做时明确选择使用旧证据或重新查询 | 重新查询可能返回不同结果；使用旧响应只是复现当时观察，不代表当前事实 |
| 可补偿的远程操作 | 保留回执并执行业务定义的补偿动作，再从当前状态继续 | 补偿是新操作，可能失败或不完整，不能称为精确回滚 |
| 邮件、付款、发布、真实设备操作等 | 尽量在操作前完成方案分叉和验证；必要时使用模拟或测试环境 | 操作后通常不能恢复到原分叉点，应仅保留历史分支或从当前现实状态发起新任务 |
| 超时或结果未知的调用 | 先按调用身份查询、对账或人工核对实际效果 | 在结果未明时不能盲目重试，也不能假设没有副作用 |

上表是场景分析，不是固定的工具分类。同一个工具可能既能读又能写；具体能否重做取决于本次操作涉及的资源、权限和环境。例如在 Git 仓库中修改源码可以用 worktree 隔离，但同一测试还可能写共享数据库或调用远程服务。

## 4. 从旧分叉点重做的候选流程

1. **核对分叉点**：检查会话、工作流、待处理调用及必要产物是否完整；确认没有结果未知的在途操作。
2. **盘点分叉点之后的效果**：找出文件、数据、远程资源和用户操作中已经发生的改变，标出无法确认的部分。
3. **为每个资源选择策略**：复制、从快照恢复到独立环境、重新构建、使用补偿操作、只读复查，或声明无法重做。不能仅因其中一项资源可回滚就认为整个任务可回滚。
4. **建立新分支的执行环境**：关联具体版本或快照，核对实际环境与分叉点要求一致。原分支的记录与环境保持可追溯。
5. **以新身份继续**：新模型请求、工具调用和费用记入新分支；旧历史作为祖先引用，不覆盖或重新标记旧操作。

若任一关键资源无法恢复或隔离，可保留**仅供查看的历史分支**；也可从当前真实状态启动带来源说明的新尝试，但不能称为“从旧分叉点重做”。是否允许用户接受状态不一致并继续，需要单独设计显式的操作与记录方式。

## 5. Runtime 与插件需要表达的能力

Runtime 负责关联会话检查点与环境状态，判断分支是否可实际执行；具体文件、数据库或外部服务的复制、恢复和核对能力由相应工具或插件提供。候选契约需至少表达：本次操作读写哪些资源、是否有副作用、是否有可查询的调用身份、是否支持快照／隔离／恢复／补偿，以及结果未知时怎样核对。

这些声明不能单独证明状态正确。Runtime 仍需记录实际执行结果和资源版本；能力未知或声明与实际不符时，分叉点先作为历史查看点，不自动开放过去状态上的重做。插件也不能通过简单的“可回滚”标志掩盖跨系统副作用。

可考虑区分以下能力，但名称和界面尚未确定：**历史可查看**、**可从快照隔离重做**、**可从当前状态另试**、**需补偿后另试**、**禁止自动重做**。这里的“可从当前状态另试”不是从过去恢复，必须在会话记录中明确标出状态差异。

## 6. 待决策问题

1. 首个试点支持哪些资源范围：只覆盖 Git 工作区，还是同时要求文件快照、数据库及远程调用？
2. 环境状态清单由 Runtime 自动收集、由插件声明，还是两者结合；如何发现插件未声明的副作用？
3. 快照何时创建、如何清理和验证；缺少分叉前快照时是否允许按构建配方重建近似环境？
4. 是否允许恢复共享环境；若允许，如何避免破坏仍在使用它的原分支或其他任务？
5. 补偿操作的失败、部分成功和重复执行怎样记入历史；是否需要人工判断才能继续？
6. 对不可恢复的外部世界，用户能否选择从当前状态派生新任务，以及界面如何避免把它误认作精确重做？

在这些问题落实前，会话树可以先记录和展示分支；**“从过去分叉并实际执行”应按资源能力逐项开放**，不能由一个全局的可分叉开关概括。
