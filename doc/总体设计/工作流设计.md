# 工作流设计

> 状态：方向草案。描述目标与设计边界，不代表功能已经实现。

整体目标与范围见[gearbox：整体定位](gearbox-定位.md)；会话记录的粒度、分叉和恢复语义见[会话历史与分支管理设计](会话历史与分支管理设计.md)。

## 1. 工作流模型

**项目核心是节点编排**：Runtime 负责启动节点、传递结果、决定合法的下一步、记录进度和停止原因。工作流可以用节点与连接表示，也可以包含循环。框架只定义两类节点的基本契约并提供必备的内置实现；具体工作流和节点实现主要由用户自定义。默认工作流只有一个 Agent Loop Node，用户需要明确验证和分工时再增加节点。

节点统一使用 **Agent Loop Node** 和 **Control Node** 命名。Control 表示按规则控制后续执行，既涵盖检查也涵盖路由。两类节点都能由用户通过插件提供自定义实现；编译、测试、Review 等是工作流中的具体步骤，不是框架预设的节点种类。

| 类型 | 职责 | 典型输出 |
| --- | --- | --- |
| Agent Loop Node | 调用模型、使用工具、迭代处理分配的任务；可使用基础内置 Loop 或用户自定义 Loop | 产物、执行记录、完成或受阻状态 |
| Control Node | 执行编译、测试、自动化检查等程序，并依据明确规则选择后继节点或结束；可使用基础内置实现或用户自定义实现 | 检查结果、证据、路由决定及原因 |

## 2. 节点契约与路由

节点间传递明确的任务输入、产物引用、检查证据和状态。Control Node 只选择工作流允许的后继；失败、无法判定、超时和无后继都有明确出口。每次回环受重试次数、模型调用或时间预算约束，避免无限循环。

Control Node 使用确定性的程序规则路由，例如按进程退出码、测试结果、文件或结构化产物校验结果判断；给定相同的已记录状态与检查结果，应得出相同的路由决定。执行验证任务的 Control Node 应实际运行检查，不能只相信 Agent Loop Node 声称“已经测试通过”，也不能仅靠 Prompt 或 skill 要求模型自行验证。检查命令本身可能失败、超时或产生不稳定结果；Runtime 需要记录观测结果，不能把测试通过扩大解释为代码绝对正确。

Review 可以由另一个 Agent Loop Node 承担；Review 的意见是输入，是否继续或结束仍由工作流声明的规则处理。专门用于决策的模型（例如 Jev）可以作为以后研究的辅助信号。只要路由依赖模型输出，这部分判断就不能称为确定性；若要保持确定性路由，应由程序校验模型输出并按已声明规则作出最终决定。是否需要模型参与路由，以及它的权限和失败处理，尚待具体场景验证。

## 3. 示例：代码修复

```text
Agent Loop Node：修改代码
        ↓
Control Node：编译、运行单元测试并路由
        ├─ 失败 → 将错误与证据交回修改代码的 Agent Loop Node
        ├─ 通过 → 可进入 Review Agent Loop Node 或后续检查
        └─ 超时／预算耗尽／无法判定 → 停止并保留现场
```

这个例子中的编译与测试是用户配置的 Control Node 工作流步骤，独立于 Agent Loop Node 是否曾在内部主动运行相同命令。路由依据本次实际检查结果，并保存命令、退出状态及必要的输出摘要。Review 节点可使用另一套模型、工具或提示配置；它仍属于 Agent Loop Node 类型。

## 4. Runtime 与插件的职责

- **执行与路由**：维护当前节点、允许的转移、节点尝试次数及停止条件。节点执行和路由决定都留下可查看的记录。
- **上下文与证据**：按节点需要组装任务目标、约束、关键产物和检查证据；原始证据可回查。会话树和分支历史由 Runtime 统一管理，具体语义见[会话历史与分支管理设计](会话历史与分支管理设计.md)。
- **恢复**：记录节点进度和在途工具操作。中断后先核对可能已有外部副作用的操作，再决定重试、等待或继续；不能默认重复执行写操作。
- **预算与控制**：对模型请求、工具执行、回环和总耗时设上限，支持取消、等待和明确的失败出口。
- **验收**：由具体 Control Node 提供可核实的通过依据；开放式任务允许人工判断，不假定所有任务都能自动证明完成。

工作流按已注册的能力标识引用节点实现。插件接口需要说明输入输出、配置、版本、所需权限、资源清理和错误语义。Runtime 在边界校验插件声明与产物，并限制其可使用的工具和工作目录。插件如何隔离、是否支持热加载及具体清单格式属于后续实现决策。

## 5. 实施顺序与验证场景

当前 Step 0 仅验证最小 Agent Loop 与只读工具的模型往返。下一步先以一个代码修复场景落实节点输入输出、检查结果、循环退出和会话分支语义，再实现最小工作流编排、树型会话记录与统一插件注册，让基础内置节点、用户自定义 Agent Loop Node 和用户自定义 Control Node 能组合运行。随后补齐持久化、恢复、上下文管理及更完整的插件生命周期。

首个可验证场景至少覆盖：编译或测试失败后回到修改节点、检查通过后进入下一步、检查超时或预算耗尽后停止；从同一历史点创建两条分支并分别继续，切换分支时恢复各自的上下文；两类用户自定义节点与内置节点在同一工作流中的组合和替换。是否需要通用 Graph DSL、多 Agent 并行、插件热加载或模型辅助路由，应由实际任务的需求和结果决定。
